# 수동 테스트 체크리스트

실제 SSO 프로필로 `npm run tauri dev` 실행 후 확인한다.

## 기본
- [ ] 첫 실행 시 17개 서비스가 모두 사이드바에 보인다
- [ ] 프로필 드롭다운에 `~/.aws/config`의 프로필이 모두 보이고, 바꾸면 그 프로필의 기본 리전으로 바뀐다
- [ ] 앱을 재시작하면 마지막 프로필/리전/활성 서비스/즐겨찾기가 복원된다
- [ ] 상태바에 프로필 · 계정 ID · 리전(전역 서비스는 global)이 보인다

## 서비스별 목록과 상세 (각 타입: 목록 표시, 행 선택 시 상세, 콘솔 열기 동작)
- [ ] EC2: Instances / Security Groups / Volumes
- [ ] S3: Buckets → 목록과 상세 확인 (버킷 더블클릭/Enter는 `S3: 버킷` 탭으로 열려요)
- [ ] Lambda: Functions
- [ ] RDS: DB Instances / DB Clusters
- [ ] ElastiCache: Replication Groups / Cache Clusters / Serverless Caches. 사이드바에서 RDS 바로 아래에 있다. Replication Groups의 엔드포인트가 클러스터 모드면 구성 엔드포인트, 아니면 기본 엔드포인트이고 상세에 읽기 엔드포인트·암호화·AUTH·사용자 그룹이 콘솔과 같다. Cache Clusters의 Memcached는 구성 엔드포인트와 노드마다 엔드포인트가 보인다. 콘솔 열기는 그 리전의 ElastiCache 첫 화면이다
- [ ] ECS: Clusters / Services / Tasks
- [ ] EKS: Clusters / Node Groups
- [ ] VPC: VPCs / Subnets
- [ ] IAM: Users / Roles / Policies
- [ ] DynamoDB: Tables
- [ ] CloudWatch Logs: Log Groups
- [ ] CloudFront: Distributions
- [ ] SQS: Queues
- [ ] SNS: Topics
- [ ] ECR: Repositories
- [ ] Route53: Hosted Zones
- [ ] Secrets Manager: Secrets (시크릿 값은 어디에도 표시되지 않는다)

## 조작
- [ ] ⌘F 필터 포커스, Esc로 필터 지우기
- [ ] 퍼지 필터: `poa`처럼 글자 일부만 순서대로 쳐도 `prod-orders-api`가 맨 위에 오고 맞은 글자가 노랗게 칠해진다. 공백으로 나눈 단어는 모두 맞아야 하고, 태그(`team=pay`)와 상태 같은 글 열로도 걸린다. 거르는 동안은 잘 맞는 순서이고 열 머리를 누르면 그 열 순서로 바뀐다(화살표가 다시 보인다)
- [ ] ⌘K(또는 툴바 ⌕): 이 프로필로 열어 본 모든 리전·종류의 리소스를 AWS 호출 없이 찾는다. `west web`처럼 리전·종류 이름도 섞어 찾고, ↑↓·Enter로 고르면 그 리전·종류로 가서 그 행이 선택되고 보인다. 앱을 다시 켜도 찾아진다(7일). 다른 곳에서 지운 리소스를 고르면 목록을 다시 읽은 뒤 "찾던 리소스가 지금 목록에 없어요"가 뜬다
- [ ] 리소스 캐시: 설정 → 리소스 캐시에서 다시 읽는 주기(기본 15분)를 바꾸면 저장된다. 그 시간이 지난 목록은 다시 열 때 바로 보이고 뒤에서 다시 읽는다. ⌘K 결과의 시각은 그 시간이 지나면 노랗다
- [ ] 하드 리셋: 설정의 [캐시 비우기] 또는 ⌘⇧R → 보이는 목록이 "불러오는 중…"부터 다시 읽히고, ⌘K가 "아직 읽어 둔 목록이 없어요"를 보이며, 앱 데이터 폴더의 `resource-index.json`이 지워진다. 그 파일에는 raw JSON(예: Lambda 환경 변수)이 없고 권한이 `-rw-------`다
- [ ] ⌘R 새로고침 후 상태바 시간이 갱신된다
- [ ] 행 선택 후 ⌘C로 ID(S3는 s3:// URI) 복사
- [ ] ↑↓로 행 이동, Enter로 S3 버킷/폴더 열기
- [ ] 스크롤바: 어느 화면에서도 스크롤바가 자리를 차지하지 않는다(마우스를 연결해 macOS가 막대를 늘 보이는 설정이어도). 스크롤하는 동안만 얇은 막대가 내용 위에 겹쳐 보이다가 1초쯤 뒤 사라지고, 보일 때 막대를 끌면 스크롤된다
- [ ] 리소스 타입 우클릭으로 즐겨찾기 추가/제거
- [ ] ⚙에서 서비스를 끄면 사이드바에서 즉시 사라진다
- [ ] 원본 데이터 보기 모달이 열리고 닫힌다

## 오류
- [ ] 세션이 만료된 SSO 프로필에서 조회 → "SSO 세션이 만료됐어요" 화면이 뜨는 동시에 자동 로그인이 시작되고, 버튼은 "브라우저에서 로그인을 완료하세요…"로 꺼져 있다 → 승인하면 자동 재조회. 취소한 뒤에는 [로그인] 버튼으로 다시 할 수 있다
- [ ] 권한 없는 타입은 "권한 없음 (액션)"만 표시하고 다른 타입은 정상 동작
- [ ] 네트워크 끊고 조회 → 네트워크 오류 + 다시 시도

## SSO 자동 로그인 (SSO 프로필이 있는 계정)
- [ ] `aws sso logout` 뒤 앱을 시작하면, 누르지 않아도 브라우저가 열리고 상단에 "<프로필>: SSO 로그인 중이에요. 브라우저에서 승인해 주세요" 배너가 뜬다. 승인하면 배너가 사라지고 목록이 저절로 불러와진다
- [ ] 세션이 만료된 다른 SSO 프로필로 바꿔도 같다. 브라우저 승인 화면에서 거부를 누르면(창만 닫으면 aws CLI가 최대 10분 기다린다) 배너가 "SSO 로그인에 실패했어요: …"로 바뀌고 [다시 로그인]·[닫기]가 보인다
- [ ] 로그인 중에 배너의 [취소]를 누르면 배너가 사라지고, 그 프로필을 다시 고르거나 오류 화면의 [로그인]을 누르기 전에는 브라우저가 다시 열리지 않는다
- [ ] 같은 `sso_session`을 쓰는 두 프로필은 한 번만 로그인한다(하나로 로그인하면 다른 프로필도 바로 읽힌다)
- [ ] `source_profile`이 SSO 프로필을 가리키는 역할 프로필은 그 원본 프로필로 로그인한다
- [ ] SSO가 아닌 프로필(액세스 키)에서는 아무것도 열리지 않는다
- [ ] IAM의 "안 쓰는 권한" 탭이나 정책 시뮬레이터에서 만료 오류가 난 뒤 로그인이 성공하면, 그 화면도 저절로 다시 불러와진다. 성공은 자동이든 버튼이든 같다
- [ ] VoiceOver: 로그인 중 줄이 실패 줄로 바뀌면 바뀐 줄만 한 번 읽는다. [취소]·[닫기]를 누른 뒤에도 키보드로 계속 움직일 수 있다
- [ ] 로그인에 성공했는데도 같은 프로필이 5분 안에 다시 만료로 실패하면, 로그인이 다시 시작되지 않는다. 대신 배너에 "로그인했는데도 자격 증명을 받지 못했어요. 프로필 설정을 확인해 주세요"가 보인다. [다시 로그인]은 바로 로그인한다. 재현하려면 `aws sso logout`을 하고, 호출 기록만 남기고 성공으로 끝나는 가짜 `aws`(실행 권한을 준 셸 스크립트로, `#!/bin/sh` 다음 줄에 `echo "$@" >> /tmp/fake-aws.log; exit 0`)를 PATH 맨 앞에 둔 터미널에서 `npm run tauri dev`를 실행한다. 로그인은 성공하지만 토큰 파일이 그대로 없어서 곧바로 다시 만료로 실패한다. `/tmp/fake-aws.log`에는 `sso login --profile …` 한 줄만 있어야 하고, [다시 로그인]을 누르면 한 줄이 더 생긴다. 확인한 뒤 가짜 `aws`를 지운다. 이 동작은 자동 테스트도 확인한다(`src/lib/useSsoLogin.test.tsx`의 "right after a successful login", `src/App.test.tsx`)
- [ ] 역할을 맡을 수 없는 역할 프로필(`source_profile`이 SSO 프로필이고 `role_arn`의 신뢰 정책이 그 주체를 허용하지 않는다)을 SSO 세션이 살아 있는 상태에서 고르면 "권한 없음 (sts:AssumeRole)"만 보인다. 로그인이 시작되지 않고 배너도 없고, 브라우저가 열리지 않으며, [로그인]·[다시 시도] 버튼도 없다
- [ ] 자격 증명을 만들 수 없는 SSO 프로필은 로그인을 열지 않는다. 토큰 전용 `sso_session` 프로필(`sso_account_id`와 `sso_role_name`이 없다. CodeCatalyst 설정이 이렇다)이나 `sso_role_name`이 빠진 프로필을 고르면 브라우저가 열리지 않고, "SSO 세션이 만료됐어요" 대신 SDK의 오류 문구("no credentials found in chain …", "not properly configured …")와 [다시 시도]가 보인다. 앱을 다시 시작해도 마찬가지다
- [ ] 앱을 쓰는 도중 세션이 만료되면(몇 시간 뒤) 다음 조회가 실패하는 순간 같은 배너와 함께 브라우저가 열린다. 전제: 그 세션에 실패나 취소 기록이 없어야 한다. 앞서 [취소]를 눌렀거나 로그인이 실패했다면, 그 프로필을 다시 고르거나 [로그인]을 누르기 전에는 몇 시간 뒤에도 열리지 않는다

## S3 탐색기 (테스트용 버킷에서만 확인)
- [ ] 리소스 탭에서 버킷 더블클릭/Enter → `S3: 버킷` 탭이 열리고, 같은 버킷은 기존 탭으로 이동, 프로필 변경 시 버킷 탭이 닫힌다
- [ ] 앱 시작 시 탭은 "리소스"만 있고, 버킷을 열면 `S3: 버킷` 탭이 생긴다. 리소스 탭으로 돌아와도 선택·스크롤이 유지된다
- [ ] 로컬 패널: 홈에서 시작, 폴더 진입/↑, 경로 직접 입력, 앱 재시작 시 마지막 경로 복원
- [ ] S3 패널: 버킷 목록 → 버킷(다른 리전 버킷 포함) → 폴더, 경로 클릭 이동, "더 보기"
- [ ] 로컬 → S3 드래그 업로드(파일, 폴더), Finder → S3 패널 드롭 업로드, [복사 →]
- [ ] S3 → 로컬 드래그 다운로드(파일, 폴더), [← 복사], 다운로드 진행률 표시
- [ ] 같은 이름이 있으면 덮어쓰기 확인(모두 덮어쓰기 / 충돌 건너뛰기 / 취소)
- [ ] 새 폴더, 파일 이름 변경, 폴더 이름 변경(하위 객체 이동), 이름 충돌 시 덮어쓰기 확인
- [ ] 삭제 확인 창의 객체 수가 맞고, 폴더 삭제 시 하위 객체까지 삭제된다
- [ ] 쓰기 권한 없는 버킷에서 업로드/삭제 시 "권한 없음 (s3:PutObject)" 등이 표시된다
- [ ] 전송 실패 항목 [재시도], [완료 항목 지우기]
- [ ] 표의 빈 공간을 클릭하면 선택이 해제되고, 이미 선택된 행을 천천히 다시 클릭해도 해제된다(더블클릭은 그대로 열기)
- [ ] 마우스 뒤로/앞으로 버튼이 포인터가 있는 패널의 탐색 기록을 이동하고, ⌘[ / ⌘]는 포커스된 패널에 적용된다
- [ ] Tab으로 패널 포커스 전환, ⌘D 비교, ⌘⌫ 삭제(S3 패널)

## 파일 비교
- [ ] 로컬↔S3, S3↔S3, 로컬↔로컬 비교 탭이 열리고, 같은 쌍을 다시 비교하면 기존 탭이 활성화된다
- [ ] 추가/삭제/변경 줄 색과 줄 안 강조, "… N줄 같음" 펼치기, ▲/▼ 및 F7/⇧F7 이동
- [ ] 같은 파일이면 "두 파일이 같아요"
- [ ] 이미지 등 바이너리·2MB 초과 파일은 크기/수정일/MD5 비교와 판정 문구
- [ ] 비교 탭의 [S3로 업로드 →]/[← 로컬로 내려받기] 후 비교가 다시 계산된다
- [ ] [외부 도구로 열기]: FileMerge, VS Code, 직접 입력 명령(설정 ⚙ → 비교 도구)
- [ ] ⌘C는 리소스 탭에서만 동작하고 탐색기/비교 탭에서는 리소스 ID를 복사하지 않는다

- [ ] [나중에] → 배너 숨김, 설정 → 업데이트 확인 → 다시 표시
- [ ] 파일 전송 중 [지금 업데이트] → "파일 전송이 끝난 뒤에" 안내, 전송 후 업데이트 → 진행률 → 앱 재시작 후 새 버전
- [ ] 오프라인에서 시작해도 오류 없이 동작, 설정에서 직접 확인하면 오류 문구 표시

## VPC 구조도
- [ ] 리소스 → VPC → VPCs에서 VPC를 더블클릭(또는 Enter)하면 `🗺 <이름>` 탭이 열리고, 같은 VPC를 다시 열면 기존 탭이 활성화된다
- [ ] AZ 열 × 퍼블릭/프라이빗/격리 행으로 서브넷이 배치되고, 서브넷 안에 EC2/NAT/RDS/ELB/Lambda/VPCE 타일이 보인다
- [ ] IGW 등은 VPC 위 테두리, S3/DynamoDB 엔드포인트·TGW·피어링은 아래 "외부 연결" 띠에 보인다
- [ ] 여러 서브넷에 걸친 ELB 등에 마우스를 올리면 같은 리소스 타일이 함께 강조된다
- [ ] 서브넷 클릭 → 오른쪽에 라우팅 테이블·경로 목록, 기본 경로 대상(IGW/NAT/TGW)이 주황으로 강조된다. 빈 곳 클릭/Esc로 선택 해제
- [ ] 휠/트랙패드로 커서 기준 확대·축소(30%~300%), 빈 곳 드래그로 이동, [맞춤] [100%] [−] [+]
- [ ] 다른 탭에 있을 때 휠/Esc가 구조도에 영향을 주지 않는다
- [ ] [PNG로 저장] → 저장 대화상자, 저장 후 "저장했어요", 취소하면 아무 일 없음. 저장된 PNG는 전체 구조도가 ×2 해상도로 들어 있다
- [ ] [새로고침]과 ⌘R이 구조도를 다시 불러온다. 권한이 없는 항목은 상단에 노란 경고로 표시된다
- [ ] 프로필을 바꾸면 VPC 탭이 닫힌다

## IAM 작업 공간: 탭과 읽기 화면
- [ ] 리소스 → IAM을 펼치면 첫 항목에 `🔐 IAM 관리`가 보이고, 누르면 `🔐 IAM · <계정ID>` 탭이 열린다. 다시 누르면 기존 탭으로 이동하고, 프로필을 바꾸면 탭이 닫힌다
- [ ] 리소스 탭 IAM의 Users / Roles / Policies에서 행을 더블클릭(또는 Enter)하면 IAM 탭이 그 사용자·역할·정책 상세로 열린다. 이미 열려 있으면 같은 탭에서 이동한다
- [ ] 첫 조회는 계정 크기에 따라 몇 초 걸리고 그동안 "IAM 정보를 불러오는 중이에요"가 보인다. 권한이 부족하면 "권한 없음 (iam:…)", SSO가 만료됐으면 자동 로그인이 바로 시작돼서 [로그인] 버튼은 "브라우저에서 로그인을 완료하세요…"로 꺼져 있다(앞서 취소했거나 실패한 세션이면 [로그인] 버튼이 켜져 있다)
- [ ] 왼쪽 메뉴: 점검(건수) · 사용자 · 그룹 · 역할 · 정책 · 누가 할 수 있나 · 변경 기록. IAM 탭은 점검 화면으로 열리고, 변경 기록은 변경을 한 번도 안 했다면 "변경 기록이 없어요"가 보인다
- [ ] 모든 화면 위에 "조직 SCP와 리소스 기반 정책은 반영하지 않아요" 안내가 보이고, 상단에 조회 시각과 [새로고침]이 있다. ⌘R(또는 ⟳)로 IAM 정보를 다시 읽는다
- [ ] 목록: 이름(경로), 상태 배지(MFA 없음·관리자급·서비스 연결 등), 마지막 사용, 정책 수(그룹은 구성원 수, 정책은 붙은 곳 수·범위·수정일). 머리글 클릭으로 정렬, ↑↓ 이동, Enter/더블클릭으로 상세, 툴바 필터(⌘F)로 이름·ARN 필터
- [ ] 사용자·역할·그룹 상세 머리글: 이름, ARN과 [복사], 배지, 만든 날, 마지막 사용, 태그. 하위 탭은 사용자 = 권한·정책·그룹·액세스 키·안 쓰는 권한, 역할 = 권한·정책·신뢰·안 쓰는 권한, 그룹 = 권한·정책·구성원
- [ ] 권한 탭: 서비스 × 목록·읽기·쓰기·권한 관리·태그 표에 허용/전체 수가 보이고 조건부(◐)·거부·경계(⊘) 수가 작게 붙는다(⊘는 거부와 권한 경계로 막힌 작업을 합친 수이고, 칸을 누르면 둘이 나뉘어 보인다). 위험 작업이 있는 서비스에 ⚠가 보이고, 서비스 필터가 동작한다. 권한 경계 등 설명은 표 위에, 카탈로그에 없는 작업은 표 아래에 보인다
- [ ] 관리자급 주체(AdministratorAccess 등)는 표 위에 "모든 서비스의 모든 작업이 허용돼요"가 보인다
- [ ] 칸을 누르면 오른쪽에 작업 목록이 열린다: 작업별 상태(허용·조건부·거부·경계로 차단), 위험 사유, 대상 리소스, 근거(정책, 상속한 그룹, Sid 또는 문장 번호, 조건 있음, Deny). 같은 칸을 다시 누르거나 ✕로 닫고, 근거 정책 이름을 누르면 그 정책 상세로 이동한다
- [ ] 정책 탭: 직접 연결 / 그룹에서 상속 / 인라인 / 권한 경계로 나뉘고, 정책 이름은 정책 상세로, 상속한 그룹 이름은 그룹 상세로 이동한다
- [ ] 그룹 탭(사용자)과 구성원 탭(그룹)의 이름을 누르면 해당 상세로 이동한다
- [ ] 액세스 키 탭(사용자): 키 ID·상태·만든 날·나이·마지막 사용·서비스/리전. 비밀 키는 어디에도 표시되지 않는다
- [ ] 신뢰 탭(역할): 서비스·계정·연동·누구나 항목과 "외부", "조건 있음", 경고(누구나 맡을 수 있음, ExternalId 조건 없음 등)
- [ ] 정책 상세: 문장 표(효과·서비스별 작업 수준과 개수·대상·조건, NotAction/NotResource 표시), JSON과 [복사], 버전(기본 표시), 붙어 있는 대상(누르면 해당 상세로 이동)
- [ ] 뒤로/앞으로: 상단 ‹ ›, ⌘[ / ⌘], 마우스 뒤로/앞으로 버튼. 정책 상세를 보고 돌아오면 보던 하위 탭과 열어 둔 칸이 그대로 있고, 다른 탭에 있을 때·글자를 입력하는 중·확인 창이 떠 있을 때는 반응하지 않는다

## IAM 작업 공간: 점검, 누가 할 수 있나, 안 쓰는 권한
- [ ] IAM 탭을 열면 점검 화면이 먼저 보인다. 카드 11개(루트 액세스 키 · 루트 MFA 없음 · MFA 없는 콘솔 사용자 · 오래된 액세스 키 · 안 쓰는 액세스 키 · 안 쓰는 사용자 · 안 쓰는 역할 · 관리자급 주체 · 권한 상승 위험 주체 · 외부에 열린 신뢰 · 붙은 곳 없는 정책)가 이 순서로 보이고, 건수와 위험/주의/참고 색이 붙는다. 문제가 없는 카드는 흐리게 "문제 없음"으로 보이고 눌리지 않는다
- [ ] 문제가 있는 첫 카드가 처음부터 선택돼 있고, 다른 카드를 누르면 아래 목록이 바뀐다. 목록은 대상 · 내용 · 조치로 나뉜다. 대상 이름을 누르면 사용자·역할·정책 상세로 이동하고(루트 계정은 글자만 보인다), 액세스 키 점검의 대상은 그 사용자의 액세스 키 탭으로 열린다. 상세를 보고 뒤로 가면 보던 카드가 그대로 선택돼 있다
- [ ] 항목마다 CLI 명령이 보이고 [CLI 복사]가 클립보드에 복사한다. 터미널에 붙여 넣어 확인한다(키 ID를 모르는 항목은 `<ACCESS_KEY_ID>`를 직접 채워야 한다). 명령이 없는 항목(루트 MFA 등)에는 복사 버튼이 없다
- [ ] 위쪽에 "기준 …" 시각이 보이고, 자격 증명 보고서를 못 읽었을 때 등의 경고는 노란 줄로 보인다. 문제가 하나도 없는 계정에서는 "발견된 문제가 없어요"가 보인다
- [ ] 오래된·안 쓰는 액세스 키 항목에서 앱이 그 키를 찾았으면 CLI 명령에 실제 키 ID가 들어가고 [키 비활성화] 빠른 조치가 보인다. 이 버튼은 바로 바꾸지 않고 "변경 미리보기" 창을 연다(아래 "직접 변경" 절 참고). 자격 증명 보고서를 못 받은 계정에서는 보고서가 필요한 점검 카드(루트 액세스 키 · 루트 MFA 없음 · MFA 없는 콘솔 사용자 · 오래된/안 쓰는 액세스 키 · 안 쓰는 사용자)가 "문제 없음" 대신 "확인할 수 없어요 (자격 증명 보고서 없음)"로 보인다
- [ ] 누가 할 수 있나: 작업 칸에 `s3:get`처럼 일부만 치면 자동 완성 목록이 뜬다(최대 50개, 앞부분이 맞는 작업이 먼저). ↑/↓로 옮기고 Enter로 고른 뒤 Enter를 한 번 더 누르면 검색한다. Esc로 목록을 닫고, 목록이 닫힌 채 ↓를 누르면 다시 열린다. 마우스로 고를 수도 있다
- [ ] 대상 ARN을 비우면 모든 리소스, 채우면 그 ARN에 적용되는 문장만 본다(예: `s3:GetObject` + `arn:aws:s3:::<테스트 버킷>/*`). 대상 ARN 칸에서 Enter를 눌러도 검색한다. 같은 조건으로 [찾기]를 다시 누르면 다시 계산한다
- [ ] 결과 표: 주체(사용자·역할과 배지) · 결과(허용 · 조건부 · 경계로 차단 · 거부) · 근거(정책, 상속한 그룹, Sid 또는 문장 번호, 조건 있음, Deny, 권한 경계). 위쪽에 찾은 작업·대상 ARN·주체 수와 안내 문구가 보이고, 해당하는 주체가 없으면 "이 작업을 할 수 있는 사용자와 역할이 없어요"가 보인다
- [ ] 결과의 주체·정책·그룹 이름을 누르면 해당 상세로 이동한다. 뒤로 가면 작업·대상 ARN 입력과 같은 결과가 그대로 있다. 다른 화면을 거쳐 메뉴로 다시 들어오면 빈 입력창으로 시작한다
- [ ] [AWS로 확인]: "AWS 정책 시뮬레이터로 확인하는 중이에요…"가 보이고, 끝나면 "AWS 확인" 열에 허용 / 허용 안 됨 / 명시적 거부가 주체마다 붙는다. 앱이 계산한 결과와 다른 주체가 없는지 본다. 시뮬레이터가 비어 있다고 한 조건 키는 칸 아래에 보인다. iam:SimulatePrincipalPolicy 권한이 없으면 "권한 없음"이 보이고 결과 표는 그대로다
- [ ] 안 쓰는 권한 탭(사용자·역할): 처음에는 설명과 [불러오기]만 보인다. 누르면 "마지막 사용 시각을 모으는 중이에요" 문구가 보이고(10~30초), 끝나면 서비스별 마지막 사용 표가 보인다. 안 쓴 서비스가 "사용 안 함 (400일)"로 맨 위에, 그다음은 마지막 사용이 오래된 순이다
- [ ] 다른 하위 탭이나 정책 상세에 갔다 와도 불러온 결과가 그대로 있고, ⌘R이나 [새로고침]이 이 작업을 다시 시작하지 않는다. [다시 불러오기]를 누르면 이전 결과를 둔 채 새로 받는다. iam:GenerateServiceLastAccessedDetails 권한이 없으면 "권한 없음"이 보이고 [불러오기]를 다시 누를 수 있다
- [ ] 통째로 안 쓰는 정책 표: 정책 이름은 정책 상세로 이동하고, 그룹에서 상속한 정책은 [떼기]가 꺼진 채 "그룹 <이름>에서 떼야 해요"와 그룹 링크가 보인다. 통째로 안 쓰는 정책이 하나도 없으면 "통째로 안 쓰는 정책이 없어요"가 보인다
- [ ] 줄인 정책 초안: JSON이 들여쓰기돼 보이고 [복사]가 동작한다. 초안 아래에 "사용 기록이 없는 권한은 빠져 있어요", "저장해도 지금 붙어 있는 정책은 그대로예요" 안내와 초안 메모(조건을 버렸다는 등)가 보인다. [떼기]와 [인라인 정책으로 저장]은 변경 미리보기를 연다(서비스 연결·Identity Center 역할이면 꺼져 있고 이유가 보인다)

## IAM 작업 공간: 직접 변경 (테스트 계정에서만 확인한다)
준비: 운영과 분리된 테스트 계정/프로필에 테스트 사용자(액세스 키 2개), 테스트 그룹, 테스트용 고객 관리형 정책을 만들어 둔다. 아래 변경은 모두 실제 IAM에 쓰기 때문에 운영 계정에서는 하지 않는다. 쓰는 자격 증명에는 해당 쓰기 권한(iam:AttachUserPolicy, iam:DetachUserPolicy, iam:PutUserPolicy, iam:DeleteUserPolicy, iam:AddUserToGroup, iam:RemoveUserFromGroup, iam:UpdateAccessKey, iam:DeleteAccessKey, iam:CreatePolicyVersion 등)이 있어야 한다.

- [ ] 미리보기 창 공통: 변경 버튼은 바로 바꾸지 않고 "변경 미리보기" 창을 연다. 요약, 호출할 API(인자 포함), 영향받는 주체별 얻는 권한(초록 ＋)·잃는 권한(빨강 －)(서비스 · 수준 · 개수와 예시 작업), "되돌릴 수 있어요/없어요"가 보인다. 미리보기를 받는 동안 [적용]은 꺼져 있다. 처음 초점은 [취소]이고 Esc가 취소하며 Enter로는 적용되지 않는다. 창이 떠 있는 동안 ⌘[ / 마우스 뒤로·앞으로는 반응하지 않는다
- [ ] 정책 붙이기: 사용자의 정책 탭 [정책 붙이기] → 이름 일부로 검색(고객/AWS 관리형 구분, 배지, 설명, 최대 100개 안내), ↑↓ Enter로도 고를 수 있다. 이미 직접 붙은 정책은 "이미 붙어 있어요"로 선택되지 않는다. 고르면 미리보기가 열리고 [적용] 뒤에 "…붙였어요 · 반영까지 몇 초 걸릴 수 있어요" 안내가 보이며, 정책 목록이 바로 한 번, 3초 뒤 한 번 더 새로 읽힌다(안내는 ✕로 닫거나 10초 뒤 사라진다. 변경 기록을 저장하지 못했을 때처럼 함께 알릴 일이 붙은 안내는 ✕로 닫을 때까지 남고, 다음 적용의 안내가 덮지 않는다). 그룹·역할에도 같은 [정책 붙이기]가 있다
- [ ] 정책 떼기: 직접 붙은 관리형 정책 줄에만 [떼기]가 있다. 그룹에서 상속한 줄은 "그룹 <이름>에서 떼야 해요" 안내와 그룹 링크만 있고(인라인이면 "지워야 해요"), 권한 경계 줄에는 버튼이 없다. 떼기 미리보기에서 잃는 권한이 빨강으로 보인다
- [ ] 인라인 정책: [인라인 정책 추가] → 이름 + JSON 편집기(CodeMirror: 줄 번호, 구문 색, JSON 오류 밑줄). Tab·Shift+Tab은 들여쓰기·내어쓰기이고 Esc 다음 Tab은 초점을 옮긴다. JSON이 틀리면 바로 빨간 안내가 나오고 [검사]·[미리보기]가 꺼진다. 이름 규칙(영문자·숫자·+ = , . @ _ -, 128자)과 같은 이름 거부("같은 이름의 인라인 정책이 이미 있어요")를 확인한다. [검사]는 AWS 정책 검사기 결과를 오류 · 보안 경고 · 경고 · 제안 순서로 보여주고, 권한이 없으면 "JSON 문법만 확인했어요"가 보인다. [미리보기] → [적용] 뒤에 편집기가 닫히고 목록에 나타난다. 미리보기에서 [취소]하면 편집기와 입력한 내용이 그대로다
- [ ] 인라인 [편집]은 현재 문서를 불러와 채우고, 바꾼 내용이 없으면 [미리보기]가 꺼져 있다. 인라인 [삭제]는 이름 입력 확인(아래)을 요구한다
- [ ] 이름 입력 확인: 인라인 정책 삭제, 액세스 키 삭제, 지금 쓰는 자격 증명(또는 그 자격 증명이 속한 그룹)의 권한을 줄이는 변경은 "확인하려면 <이름>를 입력하세요" 칸이 나온다(입력할 값은 대상의 이름이고, 액세스 키 삭제는 키 ID다). 정확히 같게 입력하기 전에는 [적용]이 꺼져 있다(대소문자·앞뒤 공백이 달라도 안 된다). 입력이 다르면 "입력한 이름이 달라요"가 보이고, 새 미리보기를 받으면 입력이 비워진다. [적용]은 빨간 위험 스타일이다
- [ ] 막힘: 서비스 연결 역할(AWSServiceRoleFor…)과 Identity Center 역할(AWSReservedSSO_…)은 정책 탭의 [정책 붙이기] [인라인 정책 추가] [떼기] [편집] [삭제]와 안 쓰는 권한 탭의 조치 버튼이 꺼져 있고 이유가 보인다. AWS 관리형 정책 상세에는 [편집]이 없다. 막힘(빨강) 경고가 있는 미리보기는 [적용]이 꺼져 있고 "막힘 경고가 있어서 적용할 수 없어요"가 보인다. 주의(노랑) 경고(CloudFormation 스택 태그, 영향받는 주체 5명 이상 등)는 적용할 수 있지만 [적용]이 위험 스타일이다
- [ ] 그룹: 사용자의 그룹 탭 [그룹에 추가](이미 속한 그룹은 선택 불가)와 각 줄 [빼기], 그룹의 구성원 탭 [사용자 추가](이미 구성원인 사용자는 선택 불가)와 각 줄 [빼기]. 미리보기에서 영향받는 주체와 권한 증감을 확인한다
- [ ] 편집기 통일: 앱에 textarea가 없다. YAML(k8s 편집·만들기, Argo YAML)·JSON(IAM 정책)은 같은 CodeMirror 편집기로 Tab이 들여쓰기이고, 창 안에서 편집기에 있을 때 Esc는 창을 닫지 않는다(Esc 다음 Tab으로 나간 뒤 Esc로 닫는다). 여러 줄 글(Argo 여러 줄 파라미터, Secret 값)은 같은 편집기의 글 모드로 Tab이 다음 칸으로 간다
- [ ] 액세스 키(사용자 → 액세스 키 탭): Active 키에는 [비활성화], Inactive 키에는 [활성화], 둘 다 [삭제]. 삭제는 "되돌릴 수 없어요"와 이름 입력 확인이 나온다. 점검 화면의 키 비활성화 빠른 조치도 같은 미리보기를 연다. 비밀 키는 어디에도 나오지 않는다
- [ ] 정책 상세 [편집]: 고객 관리형은 편집기가 현재 기본 버전 문서로 열리고, 바꾼 뒤 미리보기 → 적용하면 새 기본 버전이 만들어진다(버전이 5개면 가장 오래된 비기본 버전을 먼저 지운다는 주의 경고). 인라인 정책 상세의 [편집]은 그 정책을 가진 사용자·그룹·역할에 저장한다. 적용 후 버전 탭이 갱신된다
- [ ] 적용 실패(예: 쓰기 권한이 없는 프로필): 미리보기 창이 열린 채로 "적용하지 못했어요"와 오류가 버튼 위에 보이고, [적용]은 꺼지며 초점이 [미리보기 다시 받기]로 간다. 다시 받은 뒤에 적용할 수 있다. 실패한 시도도 변경 기록에 남는다

확인 경고와 거부는 실제 AWS에서만 끝까지 확인할 수 있다(자격 증명의 키 ID, Access Analyzer, IAM 반영 지연). 아래도 테스트 계정에서 확인한다.

- [ ] 관리자급·권한 상승: 테스트 사용자에게 AdministratorAccess를 붙이는 미리보기에 "관리자급 권한을 새로 얻는 주체: <사용자>" 확인이 나오고, 사용자 이름을 입력해야 [적용]이 켜진다. `iam:PassRole`을 `"Resource": "*"`로 여는 고객 관리형 정책을 붙이면 "권한 상승에 쓸 수 있는 권한을 새로 얻는 주체: <사용자>" 확인이 나온다
- [ ] 이 앱이 쓰는 키: 테스트 사용자의 액세스 키로 만든 프로필로 앱을 열고, 그 사용자의 액세스 키 탭에서 지금 쓰는 키를 [비활성화]하면 "적용하면 이 앱이 바로 AWS에 접근하지 못하고, 여기서는 되돌릴 수 없어요" 확인이 나오고 입력할 값은 그 키 ID다. "되돌릴 수 없어요"가 보인다. 같은 사용자의 다른 키를 [비활성화]하면 이 확인이 나오지 않는다. `role_arn` + `source_profile` 프로필에서는 원본 프로필의 키를 끄는 미리보기에도 이 확인이 나오지 않는다(알려진 한계)
- [ ] 조건부 Deny(MFA): MFA 없이 키로 접근하는 앱의 사용자가 속한 그룹에 AWS 문서의 "MFA가 없으면 거부" 정책(`BoolIfExists` `aws:MultiFactorAuthPresent` `false`)을 붙이는 미리보기에 "조건에 따라 이 앱의 자격 증명이 막힐 수 있어요 (예: MFA·IP 조건)"와 "이 변경을 되돌리는 데 필요한 권한(iam:DetachGroupPolicy)도 조건부가 돼서 이 자격 증명으로는 되돌리지 못할 수 있어요" 확인이 나오고, 그룹 이름을 입력해야 한다. "되돌릴 수 없어요"가 보인다. 확인한 뒤 [취소]한다
- [ ] 크기 한도: 사용자 인라인 정책에 공백을 뺀 글자가 2,048자를 넘는 문서를 넣으면 "사용자 인라인 정책은 모두 합쳐 공백을 뺀 2,048자까지 쓸 수 있어요…" 막힘이 나온다. 들여쓰기와 줄바꿈이 많아 전체 길이는 2,048자를 훨씬 넘지만 공백을 뺀 글자는 한도 안인 문서는 막히지 않고, 적용하면 AWS도 받아들인다. 관리형 정책 편집(6,144자)도 같은 방법으로 확인한다
- [ ] 미리보기 뒤에 바뀐 IAM: 미리보기를 연 채로 콘솔이나 CLI에서 같은 대상을 바꾼다(예: 붙이려던 정책을 먼저 붙이기, 편집하려는 고객 관리형 정책의 버전을 5개로 채우기). 앱은 읽은 지 60초가 안 된 IAM 상태를 다시 쓰므로, 미리보기를 연 뒤 1분 넘게 기다렸다가 [적용]한다(1분 안에 누르면 앱이 아직 바뀐 것을 몰라서 이 거부 대신 그대로 적용을 시도한다). 그러면 창에 "적용하지 못했어요"와 "미리보기 뒤에 IAM이 바뀌었어요. 미리보기를 다시 받아 주세요."가 보이고 IAM은 그대로다(변경 기록에도 남지 않는다). [미리보기 다시 받기] 뒤에는 바뀐 내용(이미 붙어 있다는 주의와 "되돌릴 수 없어요", 버전 삭제 호출 등)이 보이고, 그 미리보기는 적용할 수 있다
- [ ] 버전 삭제 전 정책 검사: 버전이 5개인 고객 관리형 정책을 편집한다. `access-analyzer:ValidatePolicy` 권한이 없는 프로필이면 "정책 검사를 할 수 없어 버전 삭제 뒤 저장이 실패할 수 있어요" 확인(정책 이름 입력)이 나온다. 권한이 있는 프로필에서 Access Analyzer가 오류(ERROR)를 내는 문서(예: 잘못된 리소스 ARN)로 고치면 "정책 문서에 오류가 있어 적용할 수 없어요: …" 막힘이 나오고 [적용]이 꺼진다. 두 경우 모두 지울 버전은 그대로 남아 있다
- [ ] 읽지 못한 정책: `iam:GetPolicy`를 거부한 프로필로 연다(상단에 "…정책을 불러오지 못했어요: 권한 없음 (iam:GetPolicy)" 경고). 앱이 쓰는 사용자를, 문서를 읽지 못한 관리형 정책이 붙은 그룹에서 빼는 미리보기는 영향 목록이 비어 있어도 "문서를 읽지 못한 정책이 있어 권한 변화를 다 계산하지 못했어요: <정책> (<그룹> 그룹)" 확인이 나오고 사용자 이름을 입력해야 하며, "되돌릴 수 없어요"가 보인다. 아무 데도 안 붙은 AWS 관리형 정책을 다른 테스트 사용자에게 붙이는 미리보기에도 같은 확인과 "<정책> 정책을 읽지 못했어요: 권한 없음 (iam:GetPolicy)" 주의가 나온다. 앱이 쓰는 사용자가 속한 그 그룹에 모든 작업을 거부하는(`"Effect": "Deny", "Action": "*", "Resource": "*"`) 테스트용 고객 관리형 정책을 붙이는 미리보기도 영향 목록이 비어 있어도 "문서를 읽지 못한 정책이 있어 이 앱 자격 증명의 권한 변화를 다 계산하지 못했어요: <정책> (<그룹> 그룹)" 확인이 나오고 그룹 이름을 입력해야 하며, "되돌릴 수 없어요"가 보인다. 확인한 뒤 모두 [취소]한다
- [ ] 액세스 키 빠른 조치: 오래되거나 안 쓰는 액세스 키가 있는 계정의 점검 화면에서, 그 항목의 CLI 명령에 든 `--access-key-id`가 사용자의 액세스 키 탭에 보이는 키 ID와 같다. [키 비활성화]를 누르면 "<사용자>의 액세스 키 <키 ID> 비활성화하기" 미리보기가 열리고, 적용하면 액세스 키 탭에서 그 키가 Inactive다. 점검 화면을 다시 읽으면(적용 뒤 몇 초 안에 저절로 다시 읽는다) 그 키의 항목이 사라진다. 자격 증명 보고서는 몇 시간까지 묵어서 그 키를 아직 활성으로 적고 있어도, 지금 키 목록에서 꺼진 키의 항목은 뺀다. `iam:ListAccessKeys`를 거부한 프로필에서도 점검 화면은 열리고, [키 비활성화] 없이 CLI 명령에 `<ACCESS_KEY_ID>`가 남으며, 위쪽 경고에 "일부 사용자의 액세스 키를 읽지 못해 빠른 조치를 만들지 못했어요 (<N>명): 권한 없음 (iam:ListAccessKeys)"가 보인다
- [ ] 변경 기록(🕘): 시각 · 프로필/계정 · 내용 · 결과(성공/실패, 실패 사유) · 되돌림 표시가 최신순으로 보이고, 앱을 재시작해도 남아 있다(앱 데이터 폴더의 iam-changes.jsonl). 성공한 변경에는 [되돌리기]가 있고, 누르면 "되돌리기 미리보기"가 열리며 [적용]하면 원래 항목에 "되돌림", 새 항목에 "되돌리기 기록"이 붙는다. 키 삭제처럼 되돌릴 수 없는 변경은 "되돌릴 수 없어요", 다른 계정에서 한 변경은 [되돌리기]가 꺼진 채 이유가 보인다
- [ ] 되돌리기 결과 확인: 붙이기 ↔ 떼기, 그룹 추가 ↔ 빼기, 키 상태 반대로, 인라인 저장은 이전 문서로 복원(원래 없던 정책이면 삭제), 관리형 편집은 이전 기본 버전 문서로 다시 편집된다
- [ ] 프로필을 바꾸면 IAM 탭과 함께 열려 있던 미리보기도 닫혀서, 다른 계정에 낡은 미리보기가 적용되지 않는다

## IAM 할당 표 (테스트 계정에서만 확인한다)
준비: 위 "직접 변경"과 같은 테스트 계정/프로필. 사용자 3명 이상(그중 한 명 이상은 그룹에 속함), 그룹 2개 이상, 서비스 연결 역할 하나, 고객 관리형 정책 2개 이상이 있으면 좋다. 쓰는 자격 증명에는 iam:AttachUserPolicy, iam:DetachUserPolicy, iam:AttachGroupPolicy, iam:DetachGroupPolicy, iam:AttachRolePolicy, iam:DetachRolePolicy, iam:AddUserToGroup, iam:RemoveUserFromGroup 권한이 있어야 한다. 아래 변경은 모두 실제 IAM에 쓰기 때문에 운영 계정에서는 하지 않는다. "(실제 앱에서만)"이라고 적은 줄은 jsdom이나 일반 브라우저로는 확인되지 않는 WKWebView 동작이라서, 설치한 앱(또는 `tauri build` 결과)에서 마우스와 키보드로 직접 확인한다.

- [ ] 정책 탭의 칸 상태: 왼쪽 메뉴의 `🧩 할당`(정책 아래)을 열면 [정책] [그룹 구성원] 탭이 보이고 [정책]이 먼저 열린다. 행은 사용자 · 그룹 · 역할 묶음으로 보이고(위쪽 칩 [사용자] [그룹] [역할]로 거르며, 툴바 필터는 행 이름에 퍼지로 맞고 묶음 순서는 그대로다), 열은 한 곳 이상에 직접 붙은 관리형 정책이다(붙은 주체가 많은 순, 같으면 이름순. 권한 경계로만 쓰는 정책은 열이 아니다). 칸은 ● 직접 붙음 · ◐ 그룹으로 받음 · ○ 없음이고, 직접 붙고 그룹으로도 받는 칸은 ●에 작은 ◐가 겹친다. 열 머리(정책 이름, AWS 관리형/고객 관리형, 관리자급·권한 상승 배지)를 누르면 정책 상세로, 행 머리(이름과 배지)를 누르면 주체 상세로 가고 [뒤로] 하면 보던 탭이 그대로다. 행 끝의 `인라인 N`(직접 붙은 관리형 정책을 뺀 정책 수)과 `경계`를 누르면 주체 상세로 간다. ○ 칸을 누르면 ＋(붙일 예정), ● 칸을 누르면 －(뗄 예정)로 바뀌고 같은 칸을 다시 누르면 원래대로 돌아간다. [그룹 구성원] 탭은 사용자 × 그룹(이름순)이고 ● 속함 · ○ 안 속함 · ＋ 넣을 예정 · － 뺄 예정이다
- [ ] 그룹으로 받은 칸(◐)의 팝오버: ◐만 있는 칸을 누르면 칸은 바뀌지 않고 `<그룹> 그룹에서 받아요` 팝오버와 [그룹 행으로 가기]가 열린다(그룹이 여럿이면 그룹마다 한 줄). (실제 앱에서만) 같은 칸을 한 번 더 누르면 팝오버가 닫히고, 세 번째에 다시 열린다(두 번째 누름에서 닫혔다가 곧바로 다시 열리면 안 된다). (실제 앱에서만) 마우스를 ◐ 칸 위에 올리면 받는 그룹 이름이 말풍선으로 보인다(●에 ◐가 겹친 칸도 같다). Esc, 팝오버 밖 누르기, 스크롤로도 닫힌다. [그룹 행으로 가기]는 그 그룹 행으로 옮기고, 그 행이 [그룹] 칩이나 툴바 필터로 가려져 있으면 그룹 상세를 연다. 맨 아래 행에서는 팝오버가 칸 위쪽으로 열려 창 안에 머문다
- [ ] 잠긴 행: 서비스 연결 역할(AWSServiceRoleFor…)과 Identity Center 역할(AWSReservedSSO_…) 행은 칸이 모두 꺼져 있고 이름 아래에 이유가 보인다. 눌러도 끌어도 담기지 않고, 이 행이 대상이면 행 메뉴의 [다른 주체와 같게]도 꺼져 있다
- [ ] 끌어서 칠하기: 바꿀 수 있는 칸을 누른 채 끌면 처음 칸이 된 상태(붙음 또는 안 붙음)가 지나간 칸마다 적용된다. 이미 그 상태인 칸에 걸쳐 가면 그 칸의 대기 변경은 지워지고, ◐만 있는 칸과 잠긴 행은 건너뛴다. (실제 앱에서만) 마우스를 빠르게 쓸어 내려도(한 번의 움직임으로 여러 칸을 건너뛰어도) 지나간 칸이 하나도 빠지지 않고 칠해지며, 끄는 동안 글자가 선택되지 않는다. 마우스를 떼거나 창 밖에서 떼거나 창이 포커스를 잃으면 칠하기가 끝난다. 칸을 한 번 누르면 한 번만 바뀐다(두 번 토글되지 않는다)
- [ ] 키보드: 표는 화살표로 칸·행 머리·열 머리 사이를 옮기고 Space로 토글한다. (실제 앱에서만) 칸을 마우스로 누른 뒤에도 화살표가 그 칸에서 이어진다(눌러도 초점이 표 밖이나 맨 앞으로 가면 안 된다). Shift+화살표로 범위를 넓힌 뒤 Space를 누르면 기준 칸을 토글한 결과가 범위 전체에 칠해지고, Esc는 범위를 지운다. 행 머리·열 머리에서 Enter는 상세로 간다. 행 끝 ⋯ 버튼도 Tab으로 닿고, 누르면 행 메뉴가 열린다. (실제 앱에서만) ⋯를 한 번 더 누르면 메뉴가 닫힌다(Esc도 닫는다). 행이 많은 계정에서 ↓를 계속 눌러도 초점이 보이는 자리에서 따라오고(보이는 행만 그리므로 스크롤되면서 이어진다), 머리 행과 머리 열은 스크롤해도 고정돼 있다
- [ ] "다른 주체와 같게": 행 끝 ⋯ 메뉴의 [다른 주체와 같게]로 같은 탭의 다른 주체를 원본으로 고른다(대상 자신은 목록에 없다). 원본에 직접 붙은 정책(그룹 구성원 탭은 속한 그룹) 가운데 대상에 없는 것은 붙이기·넣기로 담기고, 대상에만 있는 것은 목록으로 보이며 처음에는 모두 체크가 꺼져 있다. 체크한 것만 [담기]에서 떼기·빼기로 담긴다. 그룹으로 받은 정책은 비교하지 않는다
- [ ] 열 추가: 정책 탭의 [열 추가]로 이름 일부를 검색해 정책을 고르면 열이 더해지고, 이미 열에 있는 정책은 "이미 열에 있어요"로 선택되지 않는다. 더한 열은 열 머리를 눌러 정책 상세를 보고 [뒤로] 해도, 다른 IAM 메뉴(예: 사용자)를 보고 돌아와도 더한 순서대로 남는다. 프로필을 바꾸거나 IAM 탭을 닫았다 열면 없어진다. 장바구니에 붙이기가 담긴 정책은 열로 더한 적이 없어도 열로 보인다
- [ ] 장바구니: 칸을 누를 때마다 표 아래 막대가 `변경 N개 · <첫 변경>`(둘 이상이면 `… 외 N-1개`)로 바뀌고 왼쪽 메뉴의 `🧩 할당` 옆에 개수가 붙는다. 막대를 펼치면 변경 목록(`<정책> 붙이기 · <주체>`, `<정책> 떼기 · <주체>`, `<그룹>에 넣기 · <사용자>`, `<그룹>에서 빼기 · <사용자>`)이 나오고 항목마다 ×로 뺀다. [모두 취소]는 비운다. 다른 IAM 화면(사용자, 변경 기록 등)을 보고 돌아와도 담긴 채 남고, 프로필을 바꾸면 비워진다. 담은 뒤 콘솔이나 CLI로 같은 상태를 만들고 [새로고침]하면 "이미 붙어 있어서 뺐어요: …" 같은 알림과 함께 그 변경이 빠진다
- [ ] 묶음 미리보기와 확인 문구: [미리보기]는 `변경 N개 미리보기` 창을 연다. 변경이 적용 순서로(붙이기·넣기가 앞, 떼기·빼기가 뒤. 같은 무리 안에서는 담긴 순서) 번호와 요약으로 나열되고, 변경마다 [호출할 API N개]를 누르면 호출과 인자가 펼쳐진다. 변경별 경고, 묶음 전체의 경고, 영향받는 주체별 얻는/잃는 권한, "되돌릴 수 있어요/없어요"가 보인다. 처음 초점은 [취소]이고 Esc가 취소하며 Enter로는 적용되지 않는다. 확인 경고가 없으면 [적용]이 바로 켜진다. 확인 경고가 있을 때 변경이 모두 한 대상에 몰려 있으면(예: 한 사용자에게만 AdministratorAccess를 붙이는 묶음) 그 대상의 이름을, 대상이 여럿이면 `변경 N개 적용`을 정확히 입력해야 [적용]이 켜진다(대소문자·앞뒤 공백이 달라도 안 된다). 막힘 경고가 있으면 [적용]이 꺼지고 "막힘 경고가 있어서 적용할 수 없어요"가 보인다. 프로필을 바꾸면 열려 있던 묶음 미리보기도 닫혀서 다른 계정에 적용되지 않는다
- [ ] 중간에 멈출 때의 확인: 구성원이 없는 테스트 그룹에 AdministratorAccess를 붙여 두고, 관리자급이 아닌 사용자 하나를 [그룹 구성원] 탭에서 그 그룹에 넣기, [정책] 탭에서 그 그룹의 AdministratorAccess 떼기로 담아 [미리보기]를 연다(적용 순서가 넣기 → 떼기라서, 떼기가 실패하면 그 사용자는 관리자급이 된 채 남는다). 묶음 전체의 경고에 확인 경고 "중간에 멈추면 관리자급 권한을 새로 얻는 주체: <사용자>"가 보이고, 영향받는 주체에는 그 그룹만 나오며(영향은 처음과 끝만 비교한다) 대상이 둘이라서 `변경 2개 적용`을 정확히 입력해야 [적용]이 켜진다. 확인만 보고 [취소]해도 된다. AdministratorAccess 대신 `iam:PassRole`을 조건 없이 `"Resource": "*"`로 허용하는 정책으로 같은 묶음을 만들면(리소스나 조건을 좁힌 PassRole은 권한 상승으로 보지 않는다) "중간에 멈추면 권한 상승에 쓸 수 있는 권한을 새로 얻는 주체: <사용자>"가 보인다
- [ ] 3개 묶음 적용: 변경 3개(예: 서로 다른 사용자 둘에 정책 붙이기 + 한 사용자에서 정책 떼기)를 담아 [미리보기] → [적용]하면 창이 닫히고 "변경 3개를 적용했어요 · 반영까지 몇 초 걸릴 수 있어요" 안내가 보이며 장바구니가 비워진다. 몇 초 뒤 표가 다시 읽혀 세 칸이 바뀐 상태로 보이고, 방금 적용한 변경에 대한 "이미 … 뺐어요" 알림은 뜨지 않는다. 변경 기록(🕘)에는 세 줄이 `묶음 · 변경 3개 · <시각>` 머리 아래 한 묶음으로 모여 보인다(최신순이라 마지막에 적용한 줄이 위)
- [ ] 중간 실패: 앞 변경은 되고 뒤 변경이 거부되는 묶음으로 확인한다. 쓰는 자격 증명이 붙일 수 없는 정책(예: 쓰는 자격 증명에 `iam:PolicyARN` 조건으로 그 정책에 대해서만 `iam:AttachUserPolicy`를 거부하는 Deny를 붙여 둔다)을 붙이기 둘 가운데 두 번째로 적용되게 담는다(붙이기가 떼기보다 앞서 적용되므로, 붙이기 둘과 떼기 하나로 담는다). [적용] 뒤에 창이 닫히지 않고 "3개 중 1개를 적용하고 2번째에서 멈췄어요: <요약>: <이유>"가 보인다. 첫 변경은 적용됐고(표에서 바뀜) 나머지는 실행되지 않았으며(IAM 그대로), 장바구니에는 적용하지 못한 변경만 남는다. [적용된 1개 되돌리기]를 누르면 `변경 1개 미리보기`가 열리고 [적용]하면 첫 변경이 원래대로 돌아오며 장바구니는 그대로다. [닫기](또는 Esc)로 결과를 닫으면 남은 변경으로 [미리보기]를 다시 열 수 있다. 첫 변경에서 바로 멈추면 "3개 중 0개를 적용하고 1번째에서 멈췄어요: …"이고 [적용된 k개 되돌리기]는 없다. 실패한 변경도 변경 기록에 실패로 남는다
- [ ] 변경 기록을 저장하지 못할 때: 앱 데이터 폴더(`~/Library/Application Support/dev.finallee.magicmirror`)의 iam-changes.jsonl을 `chmod 444`로 읽기 전용으로 바꾼다(앞 단계에서 변경을 적용해 파일이 이미 있어야 한다). 서로 다른 칸 3개(예: 서로 다른 사용자 셋에 정책 붙이기)를 담아 [미리보기] → [적용]하면 창이 닫히지 않고 "3개 중 1개를 적용하고 2번째에서 멈췄어요: <둘째 변경 요약>: 변경 기록을 저장하지 못해서 멈췄어요"가 보이고, 그 아래 주의(노랑) 경고로 "변경 기록을 저장하지 못했어요: …"와 "<첫 변경 요약>: 적용했지만 변경 기록에 남기지 못했어요"가 보인다. 기록에 남은 변경이 없으니 [적용된 k개 되돌리기]는 없다. IAM에는 첫 변경만 적용됐고(표에서 바뀜) 둘째와 셋째는 쓰이지 않았으며, 장바구니에는 그 둘이 남는다. 첫 변경은 변경 기록에 없으니 되돌리려면 직접 한다. 확인이 끝나면 `chmod 644`로 파일을 되돌린다
- [ ] 변경 기록의 묶음 되돌리기: 변경 기록(🕘)에서 같은 묶음의 기록이 `묶음 · 변경 N개 · <시각>` 머리 아래 모이고(다른 기록이 사이에 끼어 있어도 한 덩어리) 머리 오른쪽에 [묶음 되돌리기]가 있다. 누르면 `변경 N개 미리보기`가 열리고(되돌리는 변경이 붙이기·넣기 먼저, 떼기·빼기 나중으로 정렬된다) [적용]하면 원래 기록마다 "되돌림"이 붙고 새 기록은 "되돌리기 기록"으로 새 묶음에 모인다. 이미 일부를 되돌린 묶음은 남은 것만 되돌린다. 모두 되돌렸거나 되돌릴 수 없는 묶음은 [묶음 되돌리기]가 꺼진 채 "되돌릴 변경이 없어요"가 보이고, 다른 계정에서 한 묶음은 꺼진 채 "다른 계정(<ID>)에서 한 변경이라 그 계정으로 열어야 되돌릴 수 있어요"가 보인다. 묶음 안 기록의 [되돌리기]는 그대로 하나씩 되돌린다
- [ ] 50개 한도: 51번째 변경을 담으려 하면 "한 번에 50개까지 담을 수 있어요"가 보이고 담기지 않는다(끌어서 칠하거나 [다른 주체와 같게]로 한꺼번에 담을 때 넘치는 만큼도 담기지 않는다). 정확히 50개까지는 [미리보기]할 수 있고, 적용하면 변경 기록에 50줄이 한 묶음으로 모인다(변경 50개가 실제로 쓰이므로 테스트용 사용자와 정책으로만 한다)

- [ ] 새로고침: 비용 탭에서 ⌘R(또는 [새로고침])을 누르면 "방금 받은 데이터"가 되고 계수기가 지금 화면의 요청 수만큼 는다(서비스별이면 3건). 리소스 탭에서 ⌘R을 누르면 계수기가 늘지 않는다
- [ ] 이번 달 1일(UTC): "이번 달 데이터가 아직 없어요"와 [지난달 보기]가 보이고, 누르면 지난달로 바뀐다
- [ ] 권한 없음: `ce:*`가 없는 프로필로 열면 "권한 없음 (ce:GetCostAndUsage)"와 필요한 권한 목록, "관리 계정이 멤버 계정의 Cost Explorer 접근을 막았을 수 있어요"가 보인다
- [ ] Cost Explorer를 한 번도 켜지 않은 계정: "Billing 콘솔에서 Cost Explorer를 처음 열면 켜져요(최대 24시간)"가 보인다
- [ ] SSO 만료: 세션이 만료된 SSO 프로필에서 탭을 열면 "SSO 세션이 만료됐어요"와 자동 로그인이 뜨고, 승인하면 화면이 다시 불러와진다
- [ ] 프로필을 바꾸면 비용 탭이 닫히고, 리전을 바꿔도 비용 탭은 그대로다

## RDS PostgreSQL 사용자 관리 1단계 (IAM 인증을 켠 테스트 클러스터에서 확인한다)
읽기만 하는 단계라 데이터베이스는 바뀌지 않는다. VPN으로 닿는 Aurora PostgreSQL 클러스터(또는 RDS for PostgreSQL 인스턴스)에 IAM 데이터베이스 인증이 켜져 있고, 프로필에 `rds-db:connect`가 있고, `rds_iam`이 있는 DB 사용자(관리까지 보려면 `rds_superuser` 멤버)가 있어야 한다. 사용자·그룹이 여러 개 있고, 그룹을 거쳐 받는 권한, NOINHERIT 구성원, CONNECT를 회수해서 못 쓰는 권한, 기본 권한이 한두 개씩 있는 테스트 데이터가 좋다.

- [ ] 탭 열기: 리소스 → RDS → DB Clusters에서 Aurora PostgreSQL(또는 Multi-AZ DB 클러스터) 행을 더블클릭하면 `🐘 <식별자>` 탭이 열리고, 같은 행을 다시 더블클릭하면 기존 탭이 활성화된다(탭이 둘 생기지 않는다). DB Instances에서 RDS for PostgreSQL 인스턴스 행도 `🐘 <식별자>` 탭을 연다. Aurora PostgreSQL 인스턴스 행을 더블클릭하면 그 인스턴스가 속한 클러스터의 탭이 열린다(인스턴스 탭은 따로 없다). MySQL이나 Aurora MySQL 행을 더블클릭하면 "PostgreSQL 엔진만 열 수 있어요" 알림이 뜨고 탭은 열리지 않는다
- [ ] 로그인 묻기와 기억: 처음 여는 대상은 "DB 사용자" 창에서 "IAM 인증으로 접속할 DB 사용자 이름을 입력하세요(예: iam_admin). 이 대상에 대해 기억해 둘게요"라고 묻고 버튼은 [연결]이다. 공백이나 `"` `<` `>` `#` `&` `%` `+`를 넣으면 "DB 사용자 이름이 올바르지 않아요…"가 보이고 [연결]이 꺼진다(63바이트가 넘으면 "DB 사용자 이름은 63바이트까지 쓸 수 있어요"). 연결하면 위쪽 줄에 DB 사용자와 "연결됨"이 보인다. 탭을 닫았다 다시 열거나 앱을 재시작하면 묻지 않고 바로 연결하고, 위쪽 줄의 [바꾸기]로 다른 사용자로 다시 연결할 수 있다. 다른 대상은 자기 DB 사용자를 따로 기억한다
- [ ] VPN을 끄고 탭을 열면 "네트워크 오류: 엔드포인트에 연결하지 못했어요(<호스트>:<포트>). VPN이 켜져 있는지 확인하세요"가 보이고 상태가 "연결 안 됨"이다(연결 시간 제한은 10초). VPN을 켜고 [다시 시도]하면 연결된다
- [ ] IAM 데이터베이스 인증이 꺼진 클러스터는 DB 사용자를 묻지도 연결하지도 않고 "이 클러스터는 IAM 데이터베이스 인증이 꺼져 있어요. RDS 콘솔에서 수정해 켠 뒤 다시 열어 주세요"를 보인다. 인스턴스는 "이 인스턴스는 …"로 시작한다
- [ ] `rds_iam`이 없거나 `rds-db:connect` 권한이 닿지 않는 DB 사용자(없는 이름 포함)로 연결하면 "IAM 인증에 실패했어요. 프로필에 rds-db:connect 권한이 있는지, DB 사용자 <사용자>에게 rds_iam이 있는지 확인하세요"가 보인다. [바꾸기]로 올바른 사용자를 넣으면 연결되고, 틀린 이름은 설정에 남지 않는다
- [ ] 역할 목록: 처음에는 사용자와 그룹이 이름순으로 보이고 `pg_*`, `rds_*`, `rdsadmin`, `rdstopmgr`, `rdsrepladmin`은 [시스템 역할 보기]를 켜야 보인다. [사용자] [그룹] 칩과 툴바 필터(⌘F, 이름에만 적용)가 동작한다. 열은 이름, 종류, 소속 그룹, 구성원, 세션, 만료일이다. 배지가 실제와 맞다: 관리자급(`rds_superuser` 멤버), IAM 인증(`rds_iam` 멤버), CREATEROLE, CREATEDB, BYPASSRLS, REPLICATION, 만료됨, 곧 만료(30일 안), 앱이 로그인한 역할(위쪽 줄의 DB 사용자)
- [ ] 역할 상세: 역할을 더블클릭(또는 Enter)하면 [개요] [구성원] [권한] [소유 객체] [세션] 탭이 있는 상세가 열린다. 개요에 속성(LOGIN, CREATEDB, CREATEROLE, INHERIT, REPLICATION, BYPASSRLS, 연결 수 제한, 만료일)과 역할별 설정과 주석이 보인다. 구성원은 속한 그룹과 이 역할의 구성원을 보이고, 상속하는 관계는 "상속", 상속하지 않고 SET ROLE은 되는 관계는 "SET ROLE로만 쓸 수 있음", PG16에서 둘 다 안 되는 관계(예: 관리자가 만든 역할을 되돌려 받은 관계)는 "상속·SET ROLE 없음"이다. 권한과 소유 객체는 데이터베이스마다 보이고, 아직 읽지 않은 데이터베이스는 [불러오기]로 읽는다. 세션은 그 역할의 연결이다. 구성원 탭의 역할 이름을 누르면 그 역할의 상세로 가고, 뒤로(⌘[)와 앞으로(⌘])가 상세와 목록을 오간다
- [ ] 권한 표: 행은 역할(사용자 먼저, 그다음 그룹, 칩과 필터는 역할 목록과 같다), 첫 열은 데이터베이스(CONNECT, CREATE, TEMP), 그다음은 스키마별 열(사용, 만들기, 읽기, 쓰기)이다. 데이터베이스 선택에는 연결할 수 있는 데이터베이스만 보인다. 출처가 그룹이나 PUBLIC뿐인 칸은 흐리다. CONNECT나 USAGE가 없어서 실제로 못 쓰는 칸에는 ⚠가 있고 마우스를 올리면 "권한은 있지만 실제로는 못 써요 (CONNECT 없음)"이 보인다. (실제 앱에서만) Tab으로 표에 들어가 화살표로 그 칸에 가면 이유("CONNECT 없음")가 칸 안에 보인다. 칸을 누르면(또는 Enter) 오른쪽에 패널이 열리고 테이블·시퀀스·함수 탭에 객체마다 가진 권한이 칩으로 나온다. 칩에 마우스를 올리면 출처가 보인다("직접 받음", "소유자", "<그룹 경로> 그룹에서 받음", "모든 역할(PUBLIC)", "pg_read_all_data"). 행 수준 보안이 켜진 테이블에는 "행 수준 보안 켜짐"이 붙는다(BYPASSRLS 역할이면 "… · BYPASSRLS라 적용되지 않아요"). Esc나 [닫기]로 패널을 닫으면 초점이 칸으로 돌아온다. 키보드: 화살표, Home/End(행의 처음과 끝), PageUp/PageDown(보이는 한 쪽), ⌘·Ctrl+Home/End(표의 첫 칸과 끝 칸)로 움직인다. (실제 앱에서만) 데이터베이스 열의 칸에서 Space, PageUp/PageDown, Home/End를 눌러도 표가 저절로 스크롤되지 않고 초점이 사라지지 않는다. 역할이 수백 개여도 스크롤이 부드럽다
- [ ] 기본 권한: 행은 (만드는 역할, 스키마 또는 "모든 스키마"), 열은 테이블, 시퀀스, 함수, 타입, 스키마이고 칸에 받는 역할과 권한이 보인다. 표 위에 "PostgreSQL 기본값: 함수는 모든 역할(PUBLIC)이 EXECUTE, 타입은 USAGE를 받아요. 기본 권한을 바꾸지 않았다면 그대로예요"가 있다. 행마다 받는 역할 하나에 문장 하나가 나온다: "<만드는 역할> 역할이 <스키마>에 새 테이블을 만들면 <받는 역할> 역할이 <권한> 권한을 받아요". PUBLIC은 "… 모든 역할(PUBLIC)이 <권한> 권한을 받아요"로 읽히고, 받는 역할을 모두 회수한 행은 "… 새 <객체>를 만들어도 아무 역할도 권한을 받지 않아요"이다. `\ddp`의 결과와 맞는지 한두 개 비교한다
- [ ] 누가 할 수 있나: 데이터베이스를 고르고 [객체 고르기]를 누른다. 입력을 멈추고 잠깐 뒤에 이름의 일부(예: `app.orders`)로 데이터베이스·스키마·테이블·시퀀스·함수를 찾고(결과가 100개에서 잘리면 안내가 나온다), 고르면 권한이 그 종류에 맞게 나온다(테이블·뷰·구체화 뷰·파티션 테이블·외부 테이블: SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER / 시퀀스: USAGE, SELECT, UPDATE / 함수: EXECUTE / 스키마: USAGE, CREATE / 데이터베이스: CONNECT, CREATE, TEMPORARY). 결과는 사용자 먼저, 그다음 그룹이고 역할마다 이유 경로가 있다: `alice ← app_write ← app_read ← 직접 받음`, `app_owner ← 소유자`, `iam_admin ← pg_read_all_data ← 미리 정의된 역할`, PUBLIC에서 받으면 `… ← 모든 역할(PUBLIC)`. NOINHERIT 구성원 관계로만 닿는 역할은 들어 있지 않다. CONNECT나 USAGE가 없는 역할은 "권한은 있지만 실제로는 못 써요" 아래에 "CONNECT 없음" 또는 "USAGE 없음"과 함께 따로 묶인다. 시스템 역할은 [시스템 역할 보기]를 켜야 보인다. 고른 데이터베이스는 권한 표, 기본 권한과 같다. 몇 개는 `has_table_privilege('<역할>', '<테이블>', 'SELECT')`의 결과와 맞는지 확인한다
- [ ] 세션: 열은 역할, 데이터베이스, 클라이언트, application_name, 상태, 시작, 대기이다. 이 앱의 연결(`application_name`이 `magic-mirror`)에는 "이 앱"이 붙고, 권한 표나 점검에서 다른 데이터베이스를 읽으면 그 연결이 늘어난다. 역할 선택으로 거르고 [다시 읽기]는 세션만 다시 읽는다(psql로 붙었다 끊으면 반영된다). `pg_read_all_stats`가 없는 DB 사용자로 보면 다른 사용자의 세션은 상태·클라이언트·시작·대기가 "—"이고 표 아래에 "빈 칸은 이 DB 사용자에게 보이지 않는 정보예요. 다른 사용자의 세션을 자세히 보려면 pg_read_all_stats 권한이 필요해요"가 보인다(그 권한을 주고 다시 읽으면 사라진다). 역할 상세의 세션 탭도 같다
- [ ] 점검: 메뉴를 열 때 모든 연결 가능한 데이터베이스를 읽는다(처음에는 "점검하는 중…"이다). 메뉴 옆 숫자는 읽은 뒤에 항목 수의 합계로 나타나고, 다른 화면에서 다시 열어도 다시 읽지 않는다. 그룹은 위험, 주의, 참고 순서로 항목 수와 함께 보인다. 항목의 역할 이름을 누르면 그 역할의 상세로, 객체(스키마·테이블·함수) 이름을 누르면 권한 표가 그 데이터베이스로 열리고 그 스키마의 열 머리가 강조되며 그 열의 첫 칸에 초점이 간다(항목이 역할도 가리키면 그 역할의 칸과 패널이 열린다). 뒤로(⌘[)가 점검으로 돌아온다. 항목이 실제와 맞는지 본다: PUBLIC에 스키마 CREATE(PG14 이하의 `public` 스키마 기본값 포함), PUBLIC에 테이블·시퀀스 권한, `rds_superuser` 멤버, CREATEROLE, BYPASSRLS, 만료됐거나 30일 안에 만료되는 로그인 사용자, 그룹도 권한도 없는 로그인 사용자, 새 테이블에는 권한이 없는 역할(기본 권한 빈틈), `search_path`를 고정하지 않은 SECURITY DEFINER 함수, `password_encryption`이 md5. 접속 권한을 회수한 데이터베이스는 "점검하지 못한 데이터베이스" 아래에 이유와 함께 나온다. 맨 아래에 "역할별 비밀번호 해시 방식과 마지막 로그인은 RDS에서 볼 수 없어 점검하지 않아요"가 있다
- [ ] 탭을 닫으면 연결이 닫힌다: 탭을 연 채로 서버에서 `SELECT count(*) FROM pg_stat_activity WHERE application_name='magic-mirror'`를 실행해 연결 수를 보고(권한 표나 점검에서 여러 데이터베이스를 읽을수록 늘어난다), 탭을 닫으면 몇 초 안에 0으로 떨어진다. 프로필을 바꿔 탭이 닫혀도 같다. 탭을 연 채 10분 동안 쓰지 않은 연결은 저절로 닫히고, 다시 읽으면 새로 연결한다
- [ ] 1단계 점검(K1)에서 고친 것:
  - 역할 상세 개요의 역할별 설정에서 `ALTER DATABASE … SET`이나 `ALTER ROLE ALL SET`으로 준 줄에는 "모든 역할"이 붙는다.
  - 역할 목록, 역할 상세, 점검이 같은 만료일(UTC 날짜)을 보인다. 한국 시간 오전 9시 전에 끝나는 만료일로 확인한다.
  - 소유자 역할을 물려받은 역할의 칸을 열면 패널의 칩에 "소유자 역할(<경로>)을 물려받음"이 보인다.
  - `WITH GRANT OPTION`으로 준 기본 권한은 표와 문장에 "(GRANT OPTION 포함)"이 붙는다.
  - `rds_superuser`에 NOINHERIT로 속한 사용자로 연결하면 역할 목록 위의 안내가 "이 사용자는 SET ROLE로만 rds_superuser 권한을 쓸 수 있어서 바꿀 수 없어요"이다.
  - [바꾸기]로 다른 DB 사용자로 다시 연결하면 세션 화면의 "이 앱" 연결이 새 사용자 것만 남는다.
  - VPN을 끈 채 점검을 다시 읽으면 첫 데이터베이스에서 네트워크 오류가 난 뒤 나머지는 기다리지 않고 같은 이유로 "점검하지 못한 데이터베이스"에 들어간다.
  - Mac을 잠재웠다가 깨우거나 VPN을 다시 연결한 뒤 [다시 읽기]를 누르면 몇 분씩 멈추지 않는다. 늦어도 90초 안에 "데이터베이스 연결이 끊겼어요. 다시 읽으면 새로 연결해요"가 보이고, 다시 읽으면 새로 연결한다.

## RDS PostgreSQL 사용자 관리 2단계 (IAM 인증을 켠 테스트 클러스터에서 확인한다)
데이터베이스를 실제로 바꾸므로 테스트용 클러스터와 테스트용 역할·테이블로만 한다. 쓰는 DB 사용자는 `rds_superuser`(또는 CREATEROLE) 멤버이고, 테이블이 있는 스키마가 하나 이상, 데이터베이스가 둘 이상 있으면 좋다.

- [ ] 읽기 전용 프리셋: 역할 목록의 [역할 만들기]에서 종류 `사용자`, 프리셋 `읽기 전용`, 스키마 하나를 골라 [미리보기]한다. 같은 권한을 가진 그룹이 없으면 "새 그룹을 만들어요"와 제안한 이름이 보이고, "기본 권한을 줄 역할"의 역할들이 체크돼 있으며 기본 권한을 바꿀 수 없는 역할은 꺼진 채 이유가 옆에 보인다. 미리보기의 SQL(그룹 만들기, 권한, 기본 권한, 구성원 넣기)을 확인하고 [적용]하면 "새 비밀번호" 창이 뜨고, [복사]하면 "복사했어요"가 보인다. 그 비밀번호로 `psql`에 그 사용자로 로그인하면(`rds_iam`이 아니므로 비밀번호로 들어간다) 고른 스키마의 테이블은 읽히고 쓰기(`INSERT` 등)는 거부된다. [닫기]로 창을 닫은 뒤에는 비밀번호가 화면 어디에도 남지 않는다(변경 기록에도 없다)
- [ ] 같은 프리셋을 다시: 방금과 같은 프리셋·스키마로 [역할 만들기]를 다시 열면 "같은 권한을 가진 그룹에 넣어요"가 처음 선택돼 있고 방금 만든 그룹이 목록에 있다. 이걸로 [미리보기]하면 SQL이 구성원 넣기뿐이고(그룹을 만들지도 기본 권한을 바꾸지도 않는다), 역할 종류를 `그룹`으로 바꾸면 대신 "같은 권한을 가진 그룹이 이미 있어요: …"가 정보로 보인다
- [ ] 칠해서 주고 거두기: [바꾸기]를 켜고 권한 표에서 칠할 권한(읽기, 쓰기 …)을 골라 칸을 눌러 담거나 끌어서 칠하고, 이미 가진 칸을 눌러 거두는 변경을 담는다. 아래 장바구니에 변경이 쌓이고 [미리보기]에서 한 묶음으로 SQL과 영향이 보인다. [적용]하면 표가 바뀐 권한으로 다시 읽힌다. 장바구니가 51개째, 다른 데이터베이스의 변경, 같은 대상에 겹치는 변경은 안내만 하고 담지 않는다
- [ ] 객체 하나에 권한 주기: 칸 패널의 [객체에 권한 주기]에서 스키마 안의 테이블 하나와 권한을 골라 담고 적용한다. 그 테이블에만 권한이 생기고(`has_table_privilege`로 확인) 같은 스키마의 다른 테이블에는 생기지 않는다. 칩의 [빼기]로 거두는 변경도 같다
- [ ] 스키마의 모든 테이블: 스키마의 모든 테이블에 읽기를 주는 변경을 미리보기하면 "새로 만드는 테이블에는 적용되지 않아요"가 보이고 [기본 권한도 담기]가 있다. 누르면 기본 권한 변경이 장바구니에 담긴다(이미 담겨 있으면 담지 않고, 담긴 줄과 겹치는 권한은 걷어 내고 담긴다). 적용한 뒤 그 스키마에 새 테이블을 만들면 권한이 따라온다
- [ ] 속성과 구성원: 역할 상세의 개요에서 CREATEDB, 연결 수 제한, 만료일을 바꿔 담아 적용하고(목록·상세·`\du`에 반영), 구성원 탭에서 그룹에 넣고 빼며, 속한 그룹의 ADMIN OPTION을 켜고 끈다. 그룹에서 빼기가 담긴 관계의 ADMIN OPTION은 꺼진 채 이유가 보인다. 시스템 역할과 구성원을 바꿀 수 없는 시스템 그룹은 꺼져 있다
- [ ] 비밀번호 재설정: 로그인 역할의 상세에서 [비밀번호 재설정]을 누르면 미리보기에 `PASSWORD '••••••••'`로 가려진 SQL이 보이고, 적용하면 "새 비밀번호" 창이 뜬다(Esc로는 닫히지 않고 [닫기]만 닫는다). 그 비밀번호로 `psql`에 로그인되고 이전 비밀번호로는 안 된다. 그룹(로그인할 수 없는 역할)에는 이 버튼이 없다
- [ ] 잠금: 다른 세션에서 `BEGIN; GRANT SELECT ON <테이블> TO PUBLIC;`을 실행하고 열어 둔다. 앱에서 그 테이블에 권한을 주는 변경을 적용하면 약 5초 안에 "다른 작업이 객체를 잠그고 있어 적용하지 못했어요. 잠시 뒤 다시 시도하세요"로 멈추고(창이 열린 채 오류가 보이고 변경 기록에 실패로 남는다), 다른 세션을 `ROLLBACK`한 뒤 [미리보기 다시 받기] → [적용]하면 적용된다
- [ ] 안전한 삭제: 한 데이터베이스에서는 테이블을 소유하고 다른 데이터베이스에는 권한만 가진 역할(과 그 역할이 준 구성원 관계)을 만든다. 역할 상세의 [삭제]를 누르면 "역할 삭제" 창이 뜨고, 넘겨받을 역할(처음은 로그인한 역할)을 바꿀 때마다 계획을 다시 받는다. 데이터베이스마다 `객체 N개 · 권한 N개 · 기본 권한 N개`와 SQL(`REASSIGN OWNED`, `DROP OWNED`, 마지막에 `DROP ROLE`)이 보이고, PG16부터는 "함께 지워지는 구성원 관계"와 "그룹에서 빠져요"가 보인다. 이 역할로 접속한 세션이 있으면 "이 역할로 접속한 세션 N개는 끊기지 않아요"가 보인다. 이름을 입력하고 [삭제]를 누르면 창이 닫히고 "역할 삭제: <이름>"이 뜨며 역할 목록으로 돌아간다. 테이블은 넘겨받은 역할의 것이 되었고(`\dt`) 다른 데이터베이스의 권한은 사라졌다. 로그인한 역할 자신을 지우려 하면 막힘 경고로 [삭제]가 꺼진다. 시스템 역할의 상세에서는 [삭제]가 꺼진 채 "시스템 역할이라 바꿀 수 없어요: <이름>"이 제목이다. 일부러 중간에 멈추게 해 본다(예: 둘째 데이터베이스에서 잠금을 잡아 둔다): 창이 열린 채 "N개 데이터베이스 중 M개를 정리하고 멈췄어요: …"와 끝낸 단계의 ✓, 나머지의 "실행하지 않음"이 보이고, 역할은 아직 있다. 정리한 데이터베이스(계획의 모든 단계)의 권한 표는 다시 읽혀 바뀐 상태로 보인다
- [ ] 세션 끊기: 다른 터미널의 `psql` 세션(다른 역할이든 같은 역할이든)을 세션 화면에서 찾아 [끊기] → [적용](확인 경고 "세션을 끊어요. 되돌릴 수 없어요")하면 그 `psql`이 연결을 잃는다. 이 앱의 세션은 [끊기]가 꺼져 있고 "이 앱의 세션은 끊을 수 없어요"가 제목이다. 이미 끝난 세션이면 "세션이 이미 끝났어요"이다. `pg_read_all_stats`가 없는 DB 사용자로 보면 다른 사용자 세션의 시작 시각이 비어 있다. 그래도 [끊기]는 되고(시작 시각 없이 pid와 역할로 확인한다) 미리보기에도 그대로 나온다. 역할 이름이 없는 세션에는 [끊기]가 없다
- [ ] 되돌리기: 변경 기록에서 권한 주기 하나, 장바구니로 적용한 묶음, 만든 역할을 각각 [되돌리기] 또는 [묶음 되돌리기]한다. 미리보기가 "되돌리기 미리보기"이고 적용하면 원래 기록에 "되돌렸어요"가 붙는다. 만든 역할은 만든 뒤에 객체나 권한이 생겼다면 "만든 뒤에 객체나 권한이 생겨서 되돌릴 수 없어요"로 막힌다. 삭제와 세션 끊기는 [되돌리기]가 꺼져 있다
- [ ] 바꿀 수 없을 때: 읽기 전용 복제본의 탭과 `rds_superuser`도 CREATEROLE도 없는 DB 사용자로 연 탭에서 [바꾸기]·[역할 만들기]·[비밀번호 재설정]·[삭제]·[끊기]·[되돌리기]가 모두 꺼져 있고 제목(마우스를 올리면 보인다)이 이유("읽기 전용 복제본이라 바꿀 수 없어요" 또는 1단계의 바꿀 수 없는 이유)이며, 위쪽에도 같은 안내가 한 번 보인다
- [ ] CREATEROLE 없는 `rds_superuser` 멤버(실제 RDS 동작 확인): `rds_superuser` 멤버이지만 CREATEROLE 속성이 없는 DB 사용자로 연결해 [역할 만들기]를 미리보기한다. 앱은 "역할을 만들 권한이 없어요. CREATEROLE이 있어야 해요"로 막는다. 서버가 실제로 같은 판단을 하는지 `psql`에서 같은 `CREATE ROLE`을 직접 실행해 확인한다. RDS가 허용한다면 앱의 규칙을 `canManage`(rds_superuser 또는 CREATEROLE)로 느슨하게 고치고 그 결과를 이 항목에 적어 둔다
- [ ] 큰 데이터베이스의 미리보기 시간: 배포하기 전에 객체가 가장 많은 데이터베이스에서 미리보기를 한 번 열어 시간을 잰다. 읽기 제한 시간(30초)보다 짧아야 한다

## EKS 쿠버네티스: 클러스터 변경 (테스트 클러스터에서만 확인한다)
준비: 운영과 분리된 테스트 EKS 클러스터와 그 클러스터에 쓰기 권한이 있는 신원, 그리고 읽기만 되는 신원을 하나 더 둔다. 테스트 네임스페이스에 Deployment(replicas 2), StatefulSet, DaemonSet, Job, CronJob, ConfigMap, Secret, Service, PDB(minAvailable = replicas)를 만들어 둔다. 아래는 모두 실제 클러스터에 쓰므로 운영 클러스터에서는 하지 않는다.

- [ ] 변경 버튼: 객체를 고르면 상세 머리에 그 종류의 변경 버튼(scale, restart, 삭제 등)이 따로 켜는 것 없이 바로 보인다. 읽기 전용 신원으로 연 탭에서는 꺼진 채 마우스를 올리면 이유(필요한 동사·리소스)가 보인다
- [ ] 미리보기 공통: 버튼은 바로 바꾸지 않고 미리보기 창(API 호출과 본문, 필드 diff, 영향, 경고)을 연다. kube-system이나 이름·네임스페이스에 `prod`가 든 대상은 이름을 똑같이 입력해야 [적용]이 켜진다. 미리보기를 띄운 채 `kubectl edit`로 spec을 바꾸고 [적용]하면 "미리보기 이후 바뀌었어요"로 멈춘다(status만 바뀐 경우는 그대로 적용된다)
- [ ] scale·restart·rollout undo: Deployment replicas를 바꿔 적용하면 상세에 "새 Pod n/m 준비" 진행이 보이고 끝나면 사라진다. restart 뒤 Pod가 새로 뜬다. rollout undo는 리비전 목록에서 골라 미리보기한다. 변경 기록에서 scale을 [되돌리기]하면 "되돌리기 미리보기"를 거쳐 원래 replicas로 돌아간다
- [ ] 삭제: Pod 삭제는 컨트롤러가 다시 만든다는 경고가 보인다. 소유자 없는 ConfigMap을 지우고 변경 기록에서 되돌리면 같은 내용으로 다시 만들어진다. Secret 삭제는 되돌릴 수 없다고 나온다. Namespace 삭제 미리보기는 이름 입력을 요구한다(확인 후 [취소])
- [ ] Job·CronJob: CronJob [바로 실행]은 이름(`<cronjob>-manual-…`, 고칠 수 있음)으로 새 Job을 만들고, 되돌리기는 그 Job을 지운다. [일시정지]·[재개]가 상태에 따라 바뀐다
- [ ] 노드: cordon·uncordon이 서로 되돌린다. drain 미리보기에 옮길 Pod, 건너뛸 DaemonSet Pod, emptyDir·컨트롤러 없음 경고, PDB로 막힐 Pod가 보이고 노드 이름 입력이 필요하다. 적용하면 Pod별 진행이 보이고, PDB로 막힌 Pod는 다시 시도하다 5분 뒤 멈춘다(옮긴 Pod는 그대로). [중단]은 지금 하는 Eviction을 마치고 멈춘다. 되돌리기는 uncordon만 된다
- [ ] YAML 편집: YAML 탭 [편집]은 status·managedFields 등을 뺀 편집기를 연다. 문법이 틀리면 밑줄과 목록이 나오고 미리보기가 꺼진다. 다른 field manager가 가진 필드를 바꾸면 충돌(필드·manager)이 보이고, 강제 적용은 이름 입력이 필요하다. Secret은 값이 가려진 채 열리고 키별 [값 보기]·[새 값 입력] 뒤에만 바뀌며, 미리보기·변경 기록 어디에도 값이 없다
- [ ] YAML로 만들기: 위쪽 [YAML로 만들기]에 문서 여러 개(Namespace + 그 안의 ConfigMap 등)를 붙여 넣으면 문서마다 미리보기가 나오고, 순서대로 적용하다 첫 실패에서 멈추며 적용한 것을 거꾸로 되돌리는 버튼이 보인다
- [ ] 셸·attach: Pod 상세 "셸" 탭에서 컨테이너를 골라 열면 bash(없으면 sh)가 뜨고 창 크기를 바꾸면 `stty size`가 따라간다. 다른 탭에 갔다 와도 세션이 살아 있다. attach는 stdin·tty가 켜진 컨테이너에서만 입력이 되고 "입력·Ctrl-C가 주 프로세스로 가요" 경고가 보인다. 변경 기록에는 열고 닫은 시각만 있고 입출력은 없다
- [ ] 노드 셸: Node 상세 [노드 셸]은 이미지(기본 busybox)를 고칠 수 있는 디버그 Pod 미리보기를 열고 노드 이름 입력을 요구한다. 열리면 `hostname`이 노드 이름이고, 닫으면 디버그 Pod가 지워진다(변경 기록에 만들기와 지우기가 남는다). 노드 이미지 레지스트리에 닿지 않는 노드면 Pod가 Ready가 안 돼 60초 뒤 실패하고 Pod는 지워진다
- [ ] port-forward: Pod·Service 상세에서 포트를 골라 열면 왼쪽 메뉴 "포트포워딩"에 `127.0.0.1:<포트>`가 보이고 브라우저로 열린다. Service 포워드는 쓰던 Pod를 지워도 다른 준비된 Pod로 다시 붙는다. [닫기]로 닫히고, 클러스터 탭을 닫거나 앱을 끄면 모두 닫힌다

## EKS 쿠버네티스: 접근 (읽기만 한다. 실제 EKS와 SSO로 확인한다)
준비: access entry와 aws-auth를 모두 쓰는 `API_AND_CONFIG_MAP` 클러스터(가능하면 `API`·`CONFIG_MAP` 클러스터도 하나씩), SSO 권한 세트로 만든 `AWSReservedSSO_*` 역할 둘 이상, IRSA ServiceAccount와 Pod Identity 연결이 있는 워크로드, 클러스터 관리자 신원과 읽기만 되는 신원.

- [ ] 신원: [접근] → [신원]에 인증 모드와 그 설명이 보인다. 같은 주체가 access entry와 aws-auth에 모두 있으면 aws-auth 쪽이 "쓰이지 않아요 · 같은 주체의 access entry가 먼저 쓰여요"로 흐리게 보이고, `API`·`CONFIG_MAP` 클러스터에서는 안 쓰는 쪽 전체가 그렇게 보인다. `{{SessionName}}` 템플릿 사용자 이름이 그대로 보인다
- [ ] SSO 묶음: `AWSReservedSSO_<권한 세트>_<해시>` 역할이 권한 세트 이름의 한 줄로 묶이고(펼치면 역할 ARN별 줄), [SSO 권한 세트로 묶기]를 끄면 모두 따로 보인다. [IAM에서 열기]가 IAM 작업 공간에서 그 역할을 연다
- [ ] access policy: AmazonEKSClusterAdmin·Admin·Edit·View 정책은 범위(클러스터 또는 네임스페이스 목록)와 함께 보이고 클러스터 전체 열의 칸이 정책에 맞게 칠해진다. 다른 정책(예: AmazonEKSAdminViewPolicy)은 "평가하지 못함"이 붙는다
- [ ] 읽지 못한 출처: access entry 목록 권한을 뺀 신원으로 열면 "이 부분을 읽지 못했어요: EKS access entry"가 보이고 나머지(aws-auth, 권한 표)는 그대로 보인다. aws-auth ConfigMap을 읽을 수 없어도 같다
- [ ] 권한 표: 위에 "RBAC과 EKS access policy만 계산해요"가 있다. 열은 클러스터 전체와 고른 네임스페이스(네임스페이스 고르기에서 찾기·추가·빼기, 최대 8열), 행은 주체(IAM·사용자·그룹·ServiceAccount)다. 종류 칩과 이름 필터가 되고 25행씩 [이전]·[다음]이다. 칸 일곱(읽기·쓰기·삭제·exec·Secret 읽기·RBAC 변경·권한 상승)은 [칸 설명]의 정의대로 칠해진다
- [ ] `kubectl auth can-i`와 대조: 권한 표의 칸 몇 개(예: 어떤 사용자의 dev 네임스페이스 읽기, Secret 읽기, exec)를 눌러 상세를 열고, 같은 신원으로 `kubectl auth can-i get secrets -n dev --as <사용자> --as-group <그룹>`을 실행해 허용 여부가 상세의 "확인한 동작"과 같은지 본다. 상세의 "바인딩 경로"가 `kubectl get rolebinding,clusterrolebinding -o wide`와 맞는다
- [ ] aggregation: `aggregate-to-view` 라벨을 단 ClusterRole을 만들면 `view`에 묶인 주체의 상세 경로에 "(그 ClusterRole에서 합쳐짐)"이 보인다(다시 읽기 후)
- [ ] 누가 할 수 있나: `get secrets`를 네임스페이스와 함께 찾으면 직접·그룹 경유·access policy로 받은 주체가 경로와 함께 나오고, `system:authenticated` 같은 기본 그룹에서 받은 권한은 그 그룹 한 줄뿐이다. [클러스터에 대조(SubjectAccessReview)]는 SubjectAccessReview를 만들 수 없는 신원에서는 꺼지고 이유가 보인다. 만들 수 있는 신원에서는 "일치 N명, 다름 M명"이 나오고 다른 줄에는 "계산은 허용, 클러스터는 거부"가 붙는다
- [ ] 워크로드 신원: IRSA 어노테이션이 있는 ServiceAccount와 Pod Identity 연결이 표에 보이고 쓰는 Pod 수가 맞다. 역할 신뢰 정책에 이 클러스터의 OIDC 공급자와 맞는 `sub`·`aud` 조건이 있으면 "동작해요", `sub`를 다른 ServiceAccount로 바꾸면 "연결돼 있지만 동작하지 않음"과 이유가, IAM 권한이 없으면 "확인하지 못함"이 보인다. 역할 이름을 누르면 IAM 작업 공간에서 열린다
## EKS 네트워크 (K6)
- [ ] 왼쪽 메뉴 "🌐 네트워크" → 로드밸런서 탭에 type이 LoadBalancer인 Service와 Ingress가 나온다. AWS Load Balancer Controller로 만든 것은 로드 밸런서 이름·ALB/NLB·리스너·대상 상태가 보이고, 행을 누르면 70% 상세에 리스너 규칙과 대상 그룹이 뜬다. 비정상 대상에는 사유가 보이고, 대상의 Pod·노드 링크가 워크로드 화면에서 그 객체를 연다
- [ ] 주소가 아직 없는 Service는 "주소 없음", 주소는 있는데 ELBv2에 없는 것(클래식 로드 밸런서 등)은 "찾지 못함"으로 나온다. 이 클러스터 태그가 붙은 짝 없는 로드 밸런서는 표 아래에 따로 나온다
- [ ] 노드·서브넷 탭: 노드마다 인스턴스 ID·AZ·서브넷이 나오고(Fargate는 인스턴스 없음), 서브넷 표의 남은 IP가 콘솔(VPC → 서브넷)과 맞다. VPC CNI 클러스터의 Pod IP 탭에서 서브넷별 Pod 수가 맞고, hostNetwork Pod는 "노드 IP"로 표시된다
- [ ] NetworkPolicy 탭: 정책이 없는 네임스페이스가 위에 표시되고, 정책을 누르면 들어오고 나가는 규칙이 요약된다
- [ ] SSO가 만료됐거나 elasticloadbalancing·ec2 읽기 권한이 없을 때 해당 부분만 "읽지 못한 부분"에 이유와 함께 나오고 쿠버네티스 쪽 화면은 그대로 보인다
- [ ] [VPC 다이어그램 열기]로 클러스터 VPC 구조도 탭이 열리고 클러스터의 노드(EC2)와 로드 밸런서에 분홍 테두리가 있다. 막대의 [강조 끄기]로 평소 모양이 된다. 상세의 [VPC 다이어그램에서 보기]는 그 로드 밸런서만 강조한다. 라이트·다크 테마 모두 확인
## EKS 쿠버네티스: Helm (테스트 클러스터에서만 확인한다)
준비: 운영과 분리된 테스트 EKS 클러스터와 쓰기 권한이 있는 신원, 읽기만 되는 신원을 하나 더 둔다. 맥에 `helm`(3.13 이상)이 있고, 테스트 네임스페이스에 작은 차트(Deployment + ConfigMap)를 `helm install`로 설치해 두었다가 `helm upgrade`를 한 번 해서 리비전을 둘 만들어 둔다. 실패한 릴리스 하나(`helm install`이 서버에서 거절당한 것)와 이름에 `prod`가 든 릴리스 하나도 둔다.

- [ ] 목록: 왼쪽 메뉴 "⎈ Helm"에서 릴리스마다 가장 높은 리비전 한 줄이 보이고 상태 배지(deployed 초록, failed 빨강, pending-* 노랑)와 차트·앱 버전·리비전이 `helm list -A`와 같다. 실패한 릴리스는 "문제 N"과 "문제 있는 것만"으로 바로 찾는다. 모든 네임스페이스를 고르면 네임스페이스 열이 생긴다. `helm`으로 업그레이드하면 10초 안에 목록이 바뀐다
- [ ] 상세: 행을 누르면 목록의 70%를 덮는 상세가 열리고 values 탭의 "사용자가 준 값"이 `helm get values`, "계산된 값"이 `helm get values --all`과 같다. 매니페스트 탭은 `helm get manifest`와 같고 Secret 값은 ••••로 가려진다. 이력 탭이 `helm history`와 같고 [보기]로 옛 리비전의 값을 읽기 전용으로 본다(위에 안내, 변경 단추는 꺼짐). 요약의 리소스 이름을 누르면 워크로드 화면에서 그 객체가 열린다(CRD처럼 이 클러스터에 없는 종류는 글로 보인다)
- [ ] helm 없음: `helm`이 PATH에 없는 상태(이름을 잠깐 바꿔서)로 앱을 열면 읽기는 되고 [업그레이드]·[롤백]·[삭제]·[차트 설치]가 꺼진 채 설치 안내가 제목으로 보인다. 읽기 전용 신원으로 연 탭에서는 `secrets`에 `create`·`delete` 권한이 없다는 이유가 보인다
- [ ] 업그레이드(values): [업그레이드]에서 값을 고치고 [미리보기]하면 `helm upgrade … --dry-run=server`로 렌더링한 결과가 객체별 필드 차이와 values 차이로 보인다. 적용하면 새 리비전이 생기고 변경 기록에는 values가 없다. 미리보기를 띄운 채 터미널에서 `helm upgrade`를 하고 [적용]하면 "미리보기 이후 바뀌었어요"로 멈춘다. `prod` 이름이나 kube-system은 이름 입력이 필요하다. 변경 기록 [되돌리기]는 롤백 미리보기를 거쳐 이전 값으로 돌린다
- [ ] 업그레이드(다른 차트): "다른 차트로"에 저장소(주소·차트·버전) 또는 OCI 주소를 넣고 미리보기한다. 없는 버전은 helm의 이유가 미리보기 오류로 보인다
- [ ] 롤백·삭제: [롤백]은 리비전을 고르면 manifest·values 차이를 보이고, 적용하면 `helm history`에 "Rollback to N"이 남는다. [삭제]는 지워질 객체 전체와 "되돌릴 수 없어요"(이력을 지울 때)를 보이고 릴리스 이름 입력이 늘 필요하다. [이력 남기기]를 켜고 지운 릴리스는 변경 기록 [되돌리기]로 롤백해 되살아난다
- [ ] 차트 설치: [차트 설치]에서 릴리스 이름·네임스페이스(없으면 만들기)·차트 위치(로컬 경로, 저장소, OCI)를 넣고 [차트 기본값 불러오기]로 values를 채워 고친 뒤 미리보기하면 서버 dry-run 결과(만들어질 객체)가 보인다. 적용하면 `helm list`에 나오고, 변경 기록 [되돌리기]는 릴리스를 삭제한다(만든 네임스페이스는 남는다)
- [ ] ConfigMap 드라이버: `HELM_DRIVER=configmap`으로 설치한 릴리스도 목록에 나오고 업그레이드·롤백·삭제가 된다

## EKS 쿠버네티스: 보안 점검 (읽기만 한다. 고치기는 테스트 클러스터에서만 확인한다)
- [ ] 왼쪽 메뉴 "🔍 보안 점검"을 열면 심각도(높음·중간·낮음)와 분류(클러스터·권한·워크로드)별 개수 카드가 나오고, 카드를 누르면 그 조건으로 목록이 걸러지고 다시 누르면 풀린다
- [ ] 클러스터 점검이 실제 EKS 설정과 맞는다: 퍼블릭 엔드포인트가 0.0.0.0/0이면 "높음", 꺼진 로그 유형(콘솔과 대조), KMS 암호화 유무, 표준 지원 종료 90일 이내(EKS 문서의 종료일과 대조), aws-auth 사용, 클러스터 생성 직후 만들어진 관리자 access entry("추정"으로 표시)
- [ ] 권한 점검이 접근 화면의 "누가 할 수 있나"와 맞는다: cluster-admin·system:masters 주체, 익명·system:authenticated에 준 권한(system:public-info-viewer 같은 기본 설정은 안 나온다), bind·escalate·impersonate·nodes/proxy·모든 Secret 읽기, Pod 생성 + 강한 ServiceAccount, 쓰이지 않는 역할, 없는 역할·ServiceAccount를 가리키는 바인딩
- [ ] 워크로드 점검: privileged, hostPath(노드 루트·런타임 소켓은 "높음"), hostNetwork, hostPID, root 실행, allowPrivilegeEscalation, request·limit·probe 없음, latest·태그 없는 이미지, default ServiceAccount 토큰 자동 마운트, NetworkPolicy 없는 네임스페이스, IMDS hop limit 2 이상 노드그룹(시작 템플릿과 인스턴스 설정)
- [ ] 시스템 네임스페이스(`kube-system`, `kube-public`, `kube-node-lease`, `amazon-*`)의 문제는 처음에 숨겨지고 "N건은 숨겼어요"가 보인다. [시스템 네임스페이스 포함]을 켜면 보인다
- [ ] [점검 항목]에서 항목을 끄면 목록과 개수에서 바로 빠지고, 앱을 다시 켜고 다른 클러스터를 열어도 그대로다(설정 `k8sSecurityChecks`). [모두 켜기]·[모두 끄기]가 분류 단위로 동작한다
- [ ] [점검 항목별로 묶기]를 켜면 항목마다 접고 펼 수 있는 묶음이 나오고, 행을 다시 누르거나 빈 곳을 누르면 선택이 풀린다
- [ ] 행을 누르면 70% 상세가 열려 증거, 왜 중요한지, 해결 방법이 보이고, 오른쪽 위 도구 모음의 [워크로드 화면에서 열기]·[IAM에서 열기]·[접근 화면에서 보기]가 대상으로 간다. AWS 리소스(클러스터·노드그룹)는 열기 단추 없이 AWS에서 고치라는 안내가 나온다
- [ ] 고칠 수 있는 항목(allowPrivilegeEscalation 미지정, 권한 없는 default ServiceAccount 토큰 자동 마운트)은 도구 모음 오른쪽 끝의 [자동으로 고치기]가 변경 미리보기를 연다: 서버 dry-run, 바뀌는 필드만의 diff, 롤아웃 주의. 적용하면 점검이 다시 읽혀 그 항목이 사라지고 변경 기록 [되돌리기]가 된다. patch 권한이 없으면 이유와 함께 꺼진다. Helm·ArgoCD가 관리하는 객체는 주의 문구에 그 도구 이름이 나온다
- [ ] AWS 읽기가 막힌 계정(예: eks:DescribeCluster 거부)에서도 화면이 뜨고, 읽지 못한 부분과 "점검하지 못한 항목"이 위에 남는다. SSO가 만료되면 로그인 버튼이 나온다
## ⚙️ Argo Workflows (personal `stg-eks`의 Argo Server, 조작은 시험용 템플릿으로만)
준비: Tailscale로 personal Argo Server(`https://argo-workflows-stg.<tailnet>.ts.net`)에 닿고, kubeconfig에 `stg-eks` context(exec가 `AWS_PROFILE=personal`)가 있다. 실제 잡(예: notification Cron)에는 조작하지 않는다. 조작 확인은 따로 만든 시험용 WorkflowTemplate(예: `echo` 한 단계, `activeDeadlineSeconds` 있음)으로만 한다.

- [ ] 연결: 사이드바 EKS 아래 `⚙️ Argo Workflows`를 누르면 탭이 하나 열리고 다시 눌러도 하나다. 서버 주소를 넣으면 2단계(인증)에서 kubeconfig context 목록이 보이고, `stg-eks`를 골라 [연결]하면 머리에 `stg-eks · v4.1.6`이 보인다. 프로필을 바꿔도 탭은 남는다
- [ ] SSO: `aws sso logout` 뒤 탭을 열면 SSO 자동 로그인이 뜨고, 승인하면 목록이 저절로 읽힌다
- [ ] 토큰: [인증 변경] → [API 토큰으로]에서 틀린 토큰은 "토큰이 만료됐거나 맞지 않아요", 맞는 토큰은 키체인에 저장된다(키체인 접근에서 `magic-mirror.argo-workflows` 항목). 서버를 빼면 키체인 항목도 사라진다. `http://` 주소는 평문 경고
- [ ] Workflows: 모든 네임스페이스의 Workflow가 실행 중·대기 → 최근 실패 → 나머지 순서로 보이고, 요약 띠의 숫자가 목록과 맞다. phase 칩·네임스페이스·원천 거르기와 퍼지 검색이 동작하고, 탭을 닫았다 열면 거르기(검색어 빼고)가 남는다. 탭이 가려지면 5초마다 읽기를 멈춘다
- [ ] 상세: 실패한 Workflow를 열면 개요(파라미터, ServiceAccount, 제한 시간, podGC, TTL, 자원 사용량), 단계 트리와 타임라인, YAML이 보인다. [실패 단계로]는 재시도로 성공한 이전 시도가 아니라 실제로 실패한 단계를 고른다. Pod가 지워진 실행의 로그는 "Pod가 지워져 로그가 없어요"
- [ ] 로그·이벤트: 실행 중인 시험 Workflow에서 로그가 따라 흐르고(follow), 검색·일시정지·JSON 줄 펼치기가 동작하며, 상세를 닫으면 흐름이 멈춘다. 이벤트 탭에 Workflow와 Pod 이벤트가 보인다(토큰 연결이면 안내만)
- [ ] CronWorkflows: `30 19 * * *` + Asia/Seoul이 "매일 19:30 (Asia/Seoul)"과 다음 5회(19:30 KST)로 보이고, 최근 실행 막대가 Workflows 목록과 맞다
- [ ] 템플릿: 시험용 템플릿의 파라미터·쓰는 Cron·최근 실행이 보이고, [실행]의 폼(enum은 고르기)으로 실행하면 새 Workflow 상세가 열린다
- [ ] 조작(시험용 Workflow만): Stop·Terminate·Suspend·Resume·Retry·다시 제출·삭제가 phase에 맞게 켜지고 확인 창을 거친다. 이름이나 네임스페이스에 `prod`가 있으면 이름을 쳐야 삭제·Stop·Terminate가 켜진다. 다시 제출하면 새 Workflow가 열린다
- [ ] 점검: 카드 6개가 보이고, 항목을 누르면 그 Workflow·Cron·템플릿 상세가 열린다
- [ ] 실시간: 시험 Workflow를 하나 제출하면 목록에 곧바로 나타나고 phase가 바뀔 때 5초를 기다리지 않고 바뀐다. 네트워크를 잠깐 끊었다 이으면 다시 붙는다. 열어 둔 상세도 그대로 따라온다
- [ ] 목록 조건: 레이블 칩(`workflows.argoproj.io/cron-workflow=…`), 이름(정확히·접두·포함), 만든 뒤·끝나기 전 날짜, [내 것만], 열 고르기(레이블 열), 행의 레이블을 누르면 그 필터가 붙는다. 200개가 넘으면 [더 보기]로 이어진다
- [ ] 여러 개 조작(시험용만): 체크박스로 둘 이상 골라 삭제하면 결과 표가 보이고, `prod`가 들어간 것이 섞이면 "선택한 N개"를 쳐야 켜진다
- [ ] 네임스페이스: 위쪽 네임스페이스 드롭다운에는 Argo 자원(Workflow·Cron·템플릿·Event Binding)이 있는 네임스페이스만 있다(stg-eks라면 `backend-dev`·`backend-stg`, `kube-system` 같은 것은 없다). 고르면 Workflows·Cron·템플릿·보관함·Events가 모두 그 네임스페이스만 읽는다
- [ ] 그래프: 실패한 Workflow에서 그래프 탭이 뜨고, 확대·축소·끌기·가로/세로·phase 거르기가 되며 노드를 누르면 노드 상세가 열린다
- [ ] 노드 동작(시험용만): 실패한 노드에서 [이 노드만 Retry], suspend 단계에서 [값 넣고 이어 가기](출력 값 폼 → 이어 감), [노드 Stop]
- [ ] 노드 상세: Containers(이미지·명령·자원), host node, memoization, 아티팩트 미리보기·내려받기(아티팩트 저장소가 있는 서버에서)
- [ ] 로그 옵션: 직전 컨테이너, 최근 N초, 시각 표시, [파일로 저장](저장 창 → 파일). archiveLogs가 켜진 서버에서 Pod가 지워진 노드의 로그가 아티팩트로 보인다
- [ ] 링크: 서버 컨트롤러 설정에 `links`가 있으면 Workflow·Pod·로그 링크가 보이고 변수(`${metadata.name}` 등)가 채워진다. [Argo UI에서 열기]·[링크 복사]·위젯 주소 복사
- [ ] YAML 편집기(시험용만): [새 Workflow]에서 예제를 골라 [검사] → [만들기], 템플릿·Cron [고치기]로 저장(충돌이면 서버 메시지), [YAML로 고쳐 다시 제출]은 새 이름으로 만들어진다
- [ ] Reports: Cron 레이블을 고르면 실행별 걸린 시간·CPU·메모리 막대가 보이고 막대를 누르면 그 Workflow가 열린다
- [ ] Argo Events: Argo Events가 없는 `stg-eks`에서 Event Sources·Sensors·Event Flow가 "이 클러스터에 Argo Events가 없어요"를 보인다. Event Bindings는 빈 목록
- [ ] User Info: 신원과 그룹이 보이고 [토큰 복사]는 클립보드에만 들어간다. Plugins는 context 연결에서 ExecutorPlugin ConfigMap을 보인다(없으면 빈 목록)

## EKS describe
- [ ] 로컬 kind에서 Deployment와 클러스터 범위 객체의 describe 탭이 같은 context의 `kubectl describe` 출력과 맞고, 다시 읽기와 객체 갱신이 동작한다.
- [ ] kubectl이 없거나 권한이 없을 때 이유와 요약·조건·컨테이너·이벤트 대체 출력이 보인다. 밝은 테마와 어두운 테마에서 확인한다.
## EKS: k9s식 탐색 (`:` 이동·한 글자 키)
- [ ] EKS 탭에서 `:`를 누르면 탭 맨 위에 입력줄이 열린다. `dep`를 치면 deployments 후보가 뜨고 Tab으로 채워 Enter하면 워크로드 화면에서 Deployment 목록이 열린다(종류 트리에 선택 표시). `:po`·`:svc`·`:no`·`:cm`·`:sec`·`:ing`·`:crd`와 `:deployments.apps`도 열린다
- [ ] `:events`·`:helm`·`:access`·`:security`·`:network`·`:forwards`·`:terminal`(처음이면 셸 하나를 띄움)·`:changes`·`:overview`가 그 메뉴로 간다. `:depoy`는 "비슷한 것: deploy…"를 보이고 이동하지 않는다
- [ ] `:ns <이름>`이 위쪽 네임스페이스를 바꾸고, `:ns ` 뒤 후보는 이 클러스터의 네임스페이스다. `:ns all`은 모두, 없는 이름은 거절한다. Esc는 닫고 커서를 돌려준다
- [ ] 다시 `:`를 누르면 최근 명령이 보이고 ↑↓로 오간다. 앱을 껐다 켜도 남는다
- [ ] 목록에 커서를 두고 j·k·g·G로 행을 옮기고 `/`가 찾기 줄을 연다. 입력칸(찾기 줄, 복제본 수 칸)에서는 글자가 그대로 입력된다. 셸 터미널 안에서는 어떤 키도 가로채지 않는다
- [ ] Pod에서 y(YAML)·l(로그)·s(셸 탭, 방식 "셸")·a(셸 탭, 방식 attach, 세션은 확인을 거쳐 열림)·⇧F(포트포워딩 대상 포트로 커서)·e(YAML 편집). Deployment에서 s는 복제본 칸으로 가서 숫자 + Enter가 scale 미리보기, r은 restart 미리보기, ⌃D는 삭제 미리보기. 어느 것도 미리보기 없이 적용되지 않는다
- [ ] 노드에서 c·u가 cordon·uncordon 미리보기를 연다(이미 그 상태면 안내만). 해당 없는 종류(ConfigMap에서 l, Pod에서 r, Deployment에서 a 등)와 행을 고르지 않았을 때는 목록 아래에 이유가 4초쯤 보인다. 권한이 없는 변경은 단추의 이유가 그대로 보인다
- [ ] `0`이 모든 네임스페이스로 바꾼다(노드처럼 네임스페이스 없는 종류에서는 안내). 다른 탭이 앞에 있을 때는 어떤 키도 EKS 목록에 닿지 않는다. ⇧⌘P·⌘/에 이 키들이 EKS 범위로 보인다
## EKS 관계 트리 (로컬 kind 또는 테스트 클러스터에서 확인한다)
- [ ] Deployment 상세의 "관계" 탭이 소유(Deployment → ReplicaSet → Pod), 참조(ServiceAccount·ConfigMap·Secret·PVC·Node), 선택(Service·PDB·NetworkPolicy), 대상(HPA) 묶음으로 보이고, 노드를 누르면 그 객체 상세가 열린다. 밝은 테마와 어두운 테마에서 확인한다
- [ ] Pod에서는 가장 위 소유자(Deployment)까지 올라가고, ConfigMap·Node·PVC에서는 그것을 쓰는 객체가 보인다(Pod와 ReplicaSet은 Deployment로 합쳐진다)
- [ ] 없는 ConfigMap·Secret을 가리키면 "없음" 배지가 뜨고 눌리지 않는다. 권한이 없는 종류(예: Service 목록)는 안내 한 줄만 뜨고 나머지 관계는 그대로 보인다
- [ ] Pod 수가 많은 Deployment(50개 넘게)에서 "일부만 보여요" 안내가 뜬다. Pod 상태가 바뀌면 관계 탭도 따라 바뀌고, [다시 읽기]가 동작한다

## EKS 터미널·플러그인 (시험용 클러스터만)
- [ ] 왼쪽 메뉴 [터미널]: 셸이 열리고 머리줄에 고정한 context가 보인다. `kubectl config get-contexts`에 그 context 하나만 나오고 `echo $KUBECONFIG`가 임시 파일이다. [새 터미널]로 탭을 더하고 ⌘⎋로 빠져나온다
- [ ] 다른 화면을 봤다 와도 터미널이 그대로이고, 탭(클러스터 탭)을 닫으면 셸이 끝나고 `ls $TMPDIR/mm-kubeconfig-*`에 파일이 남지 않는다
- [ ] 설정에서 플러그인을 추가(`kubectl describe $KIND $NAME`)하고 객체 상세 [플러그인] 메뉴에서 실행: 확장한 명령이 확인 창에 그대로 보이고, [실행] 뒤 새 터미널 탭에서 돈다. 변경 기록에 터미널 열기가 한 줄 남는다
- [ ] 플러그인 탭에서 재연결해도 확인한 명령이 다시 실행되지 않고 명령과 종료 상태가 보인다. 일반 셸은 다시 열 수 있다
- [ ] 플러그인 단축키가 ⌘/와 명령 팔레트에 이름으로 보인다. 메뉴를 연 뒤 Esc로 닫힌다
- [ ] 플러그인 명령에 `$'` 또는 `$"`를 넣으면 저장할 수 없다. 따옴표가 든 객체 이름은 `/bin/sh`에서 하나의 인자로 전달된다

## EKS 상세 설명·관계 다시 읽기
- [ ] 상세 설명과 관계 탭에서 [다시 읽기]가 상세 상단 도구 줄에만 나타나고 각 내용을 갱신한다. 밝은 테마와 어두운 테마에서 확인한다.
- [ ] 자주 바뀌는 객체의 상세 설명은 버전이 연속 변경되어도 자동 읽기가 10초보다 자주 실행되지 않는다. Secret은 가린 요약만 보인다.
- [ ] EndpointSlice의 서로 다른 네임스페이스 Pod 참조가 각각 표시되고 Pod의 관계에서 대상 EndpointSlice와 Service로 이동한다.
